Trong một dự án Data Engineering, viết được Data Pipeline và Notebook mới là một phần của công việc. Bạn còn phải quản lý thay đổi khi nhiều người cùng phát triển và đưa phiên bản đã kiểm thử đến Production mà không làm gián đoạn hệ thống. Nếu tất cả kỹ sư cùng sửa trực tiếp trong một Fabric Production Workspace, một thay đổi nhỏ trong Notebook, SQL View hoặc Pipeline có thể làm báo cáo của hàng trăm người dùng bị ảnh hưởng. Module này giải thích cách Microsoft Fabric quản lý vòng đời phát triển và phát hành.

Một hệ thống phân tích có thể lấy dữ liệu từ Dataverse, SharePoint và SQL Server, xử lý bằng Data Pipeline, Lakehouse và Notebook, rồi cung cấp cho Power BI. Khi ba người cùng phát triển, một người sửa Pipeline, một người sửa phép tính trong Notebook và người còn lại đổi một view. Những thay đổi đó phải được ghi nhận, xem xét, kiểm thử và triển khai có kiểm soát. Đây là mục tiêu của Application Lifecycle Management, tức quản lý vòng đời ứng dụng và giải pháp.

Trong Fabric, ba công cụ nền tảng là Git integration, Deployment Pipelines và Fabric REST APIs. Git integration quản lý source và version. Deployment Pipelines đưa định nghĩa những Fabric items được hỗ trợ qua các stage như Development, Test và Production. REST APIs cho phép chương trình bên ngoài gọi các thao tác đó. Cần phân biệt cả ba với Data Pipeline, vốn thực thi những hoạt động nạp và xử lý dữ liệu nghiệp vụ.

Continuous Integration, viết tắt CI: Continuous nghĩa là liên tục, Integration nghĩa là tích hợp. CI khuyến khích developer tích hợp thay đổi thường xuyên vào nhánh phát triển dùng chung, kèm các bước kiểm tra tự động hoặc review để phát hiện xung đột sớm. Ví dụ, kỹ sư A sửa Notebook làm sạch khách hàng, kỹ sư B sửa Pipeline nạp dữ liệu. Mỗi người phát triển ở nhánh riêng rồi tạo Pull Request để nhóm đánh giá trước khi merge.

Git repository là kho lưu source và lịch sử commit. Commit ghi nhận một phiên bản thay đổi. Branch là nhánh phát triển độc lập. Pull Request là yêu cầu xem xét và hợp nhất thay đổi. Merge là kết hợp các thay đổi giữa nhánh. Conflict xảy ra khi những thay đổi không thể tự hòa giải an toàn. Đây là những khái niệm thường gặp trong GitHub hoặc Azure DevOps, và Fabric Git integration sử dụng các cơ chế tương tự.

Đừng nhầm Git integration với một hệ thống tự kiểm thử. Git giúp lưu và đồng bộ source, nhưng muốn chạy kiểm tra cú pháp, unit tests hoặc data contract checks khi có Pull Request thì cần bổ sung công cụ CI, chẳng hạn GitHub Actions hoặc Azure Pipelines. Một Pull Request được merge không mặc nhiên bảo đảm Notebook có thể chạy đúng với dữ liệu Production.

Continuous Delivery nghĩa là liên tục chuẩn bị và chuyển các thay đổi đã tích hợp đến trạng thái sẵn sàng phát hành. Continuous là liên tục, Delivery là bàn giao hoặc cung cấp. Ví dụ, phiên bản từ main được triển khai sang Test, chạy integration tests và chờ người quản lý phê duyệt đưa lên Production. Sự chấp thuận của con người vẫn có thể là bước bắt buộc trong Continuous Delivery.

Continuous Deployment cũng dùng viết tắt CD trong một số ngữ cảnh, nhưng Deployment nghĩa là triển khai tự động. Trong mô hình này, sau khi thay đổi vượt qua các bài kiểm thử và điều kiện đã cấu hình, hệ thống tự phát hành đến Production. Điểm khác với Continuous Delivery là việc phát hành không cần một bước thủ công riêng khi mọi điều kiện đã đạt. Với dữ liệu tài chính hoặc báo cáo quản trị quan trọng, một cổng phê duyệt Production có thể phù hợp hơn tự động hoàn toàn.

Trong Fabric, Git integration được cấu hình ở cấp Workspace. Một Workspace có thể kết nối một Git repository, một branch và một folder tại cùng một thời điểm theo cơ chế được hỗ trợ. Ví dụ, Development Workspace kết nối branch main của repository, còn một developer muốn làm feature riêng có thể tạo branch feature-clean-customer và một isolated Workspace. Việc tách không gian phát triển giúp hạn chế ghi đè công việc của nhau.

Khi thiết lập kết nối Git, cần có quyền phù hợp trên Fabric Workspace và trên Git repository. Microsoft Fabric hỗ trợ GitHub và Azure DevOps trong những hình thức được công bố. Administrator có thể quản lý tenant settings cho phép đồng bộ item với Git và giới hạn provider. Một người có quyền Contributor trên Fabric không tự động có quyền push vào GitHub. Hai hệ thống phải được cấp quyền đúng riêng biệt.

Hai thao tác Git dễ nhầm nhất là Commit to Git và Update from Git. Commit to Git gửi những thay đổi của các item từ Fabric Workspace lên branch Git được kết nối. Update from Git đưa những định nghĩa thay đổi từ Git branch vào Workspace. Đây là hai chiều khác nhau. Nếu bạn sửa Notebook trong Fabric, muốn lưu thay đổi lên repository thì Commit. Nếu người khác merge code mới vào main, muốn Workspace nhận thay đổi thì Update.

Git integration có thể báo những thay đổi chỉ ở Workspace, những thay đổi chỉ ở Git và các conflict. Nếu cùng một item được sửa ở cả hai phía, không nên chọn ghi đè tùy tiện. Cần xem diff và quyết định cách hòa giải để không làm mất logic của người khác. Một quy tắc làm việc thực tế là mỗi developer dùng feature branch và isolated Workspace cho thay đổi lớn, rồi tích hợp qua Pull Request.

Fabric còn có tính năng branch out giúp tạo feature branch và Workspace phát triển riêng từ giao diện khi đủ quyền. Developer cũng có thể chỉnh code bằng VS Code hoặc dùng Power BI Desktop trong những trường hợp item hỗ trợ rồi push vào Git. Sau khi Pull Request được review và merge, cần đồng bộ Integration Workspace từ main. Merge trên Git không có nghĩa tất cả Workspace đang tồn tại sẽ tự thay đổi ngay.

Một giới hạn rất quan trọng: Git integration quản lý định nghĩa Fabric items được hỗ trợ, không phải bản sao toàn bộ dữ liệu trong OneLake. Nếu Lakehouse chứa mười triệu dòng dữ liệu, commit định nghĩa Lakehouse không đưa mười triệu dòng ấy vào repository. Các credentials, secrets và tokens cũng không nên lưu thẳng trong source. Ngoài ra, không phải item và capability nào của Fabric đều có cùng mức hỗ trợ Git; phải kiểm tra danh sách hỗ trợ thực tế.

Sau version control là Deployment Pipelines. Tên này rất dễ nhầm với Data Pipelines trong Data Factory. Data Pipeline thực thi Copy Data, Dataflow hoặc Notebook để xử lý dữ liệu nghiệp vụ. Deployment Pipeline triển khai định nghĩa Fabric items qua các giai đoạn của lifecycle. Chúng giải quyết hai bài toán khác nhau; không thể dùng Deployment Pipeline như công cụ copy mọi bản ghi từ bảng Development sang bảng Production.

Một Deployment Pipeline thường có ba stage: Development, Test và Production. Mỗi stage được gắn với Workspace tương ứng. Một tổ chức có thể cần nhiều hoặc ít stage hơn trong giới hạn Fabric hỗ trợ. Development dùng để phát triển. Test để kiểm tra chức năng và tác động thay đổi. Production là nơi phục vụ dữ liệu và báo cáo thật. Việc phân biệt Workspaces giúp giảm rủi ro thử nghiệm trực tiếp lên Production.

Quy trình triển khai thường bắt đầu bằng việc phát triển Lakehouse, Notebook hoặc Pipeline ở Development. Sau khi kiểm tra, bạn chọn những item cần deploy đến Test. Ở Test, nhóm xác minh connections, thông số và dữ liệu đầu ra. Sau khi đạt điều kiện phê duyệt, bạn deploy đến Production. Deployment History và cơ chế so sánh nội dung giữa stage giúp nhóm biết item nào đã được đưa sang môi trường nào.

Deployment Pipeline triển khai định nghĩa item được hỗ trợ; nó không tự copy toàn bộ dữ liệu Lakehouse. Nếu bạn tạo Lakehouse ở Development rồi deploy sang Test, item Lakehouse ở Test có thể tồn tại nhưng không chứa mười triệu dòng của Development. Cần một Data Ingestion Pipeline hoặc phương thức nạp dữ liệu phù hợp để chuẩn bị dữ liệu cho từng môi trường. Đây là bẫy thi quan trọng vì từ triển khai thường bị hiểu nhầm thành sao chép dữ liệu.

Fabric cần biết item ở stage trước tương ứng với item nào ở stage sau. Cơ chế Item Pairing giúp liên kết những bản đại diện của cùng item giữa các stage. Chỉ vì hai item cùng tên không đồng nghĩa chúng đã được paired đúng. Khi không có pairing và cấu hình phù hợp, deployment có thể không cập nhật đối tượng bạn đang mong đợi. Vì thế, nên tổ chức quy trình triển khai có kiểm soát từ đầu.

Các Fabric items có thể phụ thuộc nhau. Ví dụ, Power BI Report sử dụng Semantic Model, còn Semantic Model đọc dữ liệu từ Lakehouse. Autobinding là cơ chế giúp liên kết những item tương ứng khi deployment trong các trường hợp hỗ trợ. Tuy nhiên, không phải liên kết hoặc connection nào đều được sửa tự động. Sau khi deploy, phải kiểm tra Report, Semantic Model, Notebook và Pipeline có trỏ đúng resource của target Workspace hay không.

Một rủi ro Production là Report được deploy sang Production nhưng vẫn tham chiếu đến dữ liệu Development. Deployment được đánh dấu thành công không có nghĩa các nguồn dữ liệu đã được cấu hình đúng. Vì vậy, cần có kiểm tra connections, identity và environment-specific settings ở từng stage. Những tùy chọn như Deployment Rules và Variable Library có thể giúp tách cấu hình môi trường khỏi định nghĩa xử lý trong những trường hợp được Fabric hỗ trợ.

Ví dụ, Data Pipeline ở Development kết nối tới sql-dev, ở Test kết nối sql-test và ở Production kết nối sql-prod. Bạn muốn giữ một logic Pipeline nhưng thay thông tin kết nối theo môi trường. Có thể cân nhắc cơ chế cấu hình theo stage, deployment rules hoặc Variable Library tùy loại item và tính năng được hỗ trợ. Không nên mặc định mọi loại rule áp dụng được cho mọi Fabric item, và cũng không nên xem Fabric Variable Library giống hệt Environment Variables của Power Platform.

Một kiến trúc thường được Microsoft hướng dẫn là chỉ kết nối Git cho Development Workspace. Khi code trên main được cập nhật, Development Workspace đồng bộ từ Git. Sau đó dùng Deployment Pipelines đưa item từ Development sang Test và Production. Nhưng đây không phải kiến trúc duy nhất. Một số tổ chức chọn mô hình từng stage có branch riêng hoặc deployment trực tiếp từ item definitions. Cách chọn phụ thuộc nhu cầu quản trị và quy mô giải pháp.

Fabric cung cấp REST APIs để tự động hóa các bước này. REST là Representational State Transfer: Representational là cách biểu diễn, State là trạng thái và Transfer là truyền tải; đây là phong cách thiết kế API. API là Application Programming Interface: Application là ứng dụng, Programming là lập trình và Interface là giao diện. Fabric REST APIs cho phép GitHub Actions hoặc Azure Pipelines kiểm tra trạng thái Workspace, đồng bộ Git và kích hoạt deployment.

Trong nhóm Git APIs, Get Status giúp biết Workspace và branch có phiên bản thay đổi nào. Update From Git đưa thay đổi từ remote vào Workspace. Commit To Git lưu thay đổi Workspace lên branch. Các API sử dụng những định danh như Workspace ID và commit hash để bảo vệ quá trình đồng bộ. Nếu trạng thái đã thay đổi kể từ khi bạn đọc, cần lấy lại thông tin mới thay vì áp dụng mù một bản cũ.

Nhóm Deployment Pipelines APIs giúp tự động deploy từ một source stage sang target stage. Bạn có thể chỉ định những item cần triển khai hoặc triển khai theo phạm vi được API hỗ trợ. Quyền thực thi phải phù hợp với Deployment Pipeline và các Workspace liên quan. Một workflow chạy bằng service principal cũng cần kiểm tra rằng loại item và API đang sử dụng hỗ trợ identity đó.

Một điểm rất quan trọng trong automation là Long-Running Operation, viết tắt LRO. Long nghĩa là dài, Running là đang thực hiện, Operation là tác vụ. Một lần gọi API có thể trả mã HTTP 202 Accepted. HTTP là Hypertext Transfer Protocol: Hypertext là siêu văn bản, Transfer là truyền tải và Protocol là giao thức. Mã 202 cho biết yêu cầu đã được chấp nhận để xử lý, chứ không có nghĩa deployment đã thành công.

Khi nhận 202, workflow cần theo dõi Operation ID hoặc địa chỉ giám sát được trả về, tuân thủ khoảng Retry After nếu có và chờ trạng thái kết thúc. Chỉ sau khi operation thật sự Succeeded mới tiếp tục bước kiểm thử hoặc phát hành tiếp. Nếu chỉ nhìn HTTP 202 rồi đánh dấu GitHub Actions job là thành công, bạn có thể báo sai rằng Fabric Production đã cập nhật trong khi deployment vẫn chạy hoặc đã thất bại.

Một quy trình Production có thể bắt đầu khi Pull Request được merge vào main. GitHub Actions thực hiện validations, gọi API để đồng bộ Development Workspace, triển khai sang Test, chạy integration tests và chờ phê duyệt Production. Sau đó API triển khai phiên bản đã được kiểm thử sang Production. Trong mô hình đó, GitHub Actions điều phối release; Fabric APIs thực hiện hành động; Deployment Pipelines quản lý stages; và Data Pipelines xử lý dữ liệu sau khi giải pháp được triển khai.

Bảo mật cần được đưa vào ngay từ đầu. Không hardcode access tokens trong repository. Identity gọi Fabric APIs phải có quyền cần thiết, không phải chỉ có token là đủ. Với GitHub Actions, có thể quản lý secrets hoặc cơ chế federated identity phù hợp. Những connection tới nguồn dữ liệu Production cũng cần được cấu hình riêng và chỉ cấp quyền tối thiểu cho workload.

Bài thực hành chính thức của module tập trung vào Deployment Pipelines, không yêu cầu viết GitHub Actions hay gọi API. Người học tạo ba Workspaces riêng cho Development, Test và Production, sau đó tạo một Deployment Pipeline và gắn đúng Workspace vào từng stage. Tiếp theo, tạo Lakehouse tên LabLakehouse trong Development, sử dụng sample data, rồi lần lượt deploy Lakehouse sang Test và Production.

Sau khi deploy, bài thực hành yêu cầu xác nhận item Lakehouse xuất hiện ở cả ba Workspace và kiểm tra lịch sử hoặc trạng thái so sánh giữa các stage. Nhưng dữ liệu mẫu ở Development không tự động xuất hiện đầy đủ trong Lakehouse ở Test và Production. Đây chính là bài học cần hiểu từ lab: triển khai item definition khác với di chuyển dữ liệu.

Một lỗi thường gặp là không gán được Workspace vào stage vì thiếu quyền hoặc Workspace đã thuộc một Deployment Pipeline khác. Một lỗi khác là deployment thành công nhưng Notebook hoặc Report tham chiếu sai nguồn. Cũng có trường hợp item target không được paired đúng. Khi xử lý, cần xem Workspace role, Pipeline role, pairing và dependencies trước khi cho rằng tool deployment bị lỗi.

Hãy xét ba câu hỏi scenario. Nếu nhóm cần lưu lịch sử sửa Notebook, làm việc trên feature branches và duyệt Pull Request, hãy chọn Git integration. Nếu cần đồng bộ định nghĩa từ repository vào Fabric Workspace, chọn Update from Git. Nếu cần đưa những item đã kiểm thử qua Development, Test và Production, chọn Deployment Pipeline, không chọn Data Pipeline.

Cuối cùng, nếu cần tự động hóa việc deploy sau khi CI tests thành công, hãy kết hợp một hệ thống automation như GitHub Actions với Fabric REST APIs. Nhớ kiểm tra trạng thái cuối của Long-Running Operation. Một thiết kế CI/CD an toàn phải quản lý source, staging, quyền, cấu hình môi trường, kiểm thử và dữ liệu tách biệt. Chỉ khi phân biệt rõ những trách nhiệm đó, bạn mới tránh nhầm một release thành công về mặt định nghĩa item với một hệ thống Production thật sự sẵn sàng phục vụ người dùng.
