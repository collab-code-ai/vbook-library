Unit 1 — Introduction

Unit này dạy gì

Quản lý Semantic Model như một tài sản phần mềm: thay đổi có version, kiểm thử, triển khai có kiểm soát và giám sát sau phát hành.

Nội dung chính trong unit

Nếu ba Developers cùng sửa PBIX và Publish trực tiếp Production, có thể xảy ra overwrite, KPI thay đổi không được review, thiếu rollback và report dependencies bị lỗi. Microsoft Learn đưa ra bốn giai đoạn:

  1. Develop: tạo Shared Models, Reports, PBIP/TMDL và Git History.
  2. Validate: kiểm tra Metadata, Relationships, DAX, Business Values bằng SemPy/XMLA/External Tools.
  3. Deploy: chuyển phiên bản được duyệt qua Development, Test, Production với Rules.
  4. Monitor: theo dõi Refresh, Data Freshness, Lineage, Errors, Change Impact.

Ví dụ thay [Revenue] = SUM(Sales[Revenue]) thành [Revenue] = SUM(Sales[Revenue]) - SUM(Sales[RefundAmount]) có thể hợp lệ cú pháp nhưng thay đổi định nghĩa KPI. ALM giúp kiểm soát và truy vết thay đổi, không tự xác nhận đúng nghiệp vụ.

Unit 2 — Create reusable Power BI assets

Unit này dạy gì

Chọn Shared Semantic Model, Power BI Template hoặc Data Source File để tái sử dụng phần thích hợp của giải pháp.

Shared semantic models

Nhiều Reports (Sales, Finance, Executive, Regional) dùng một Model trung tâm chứa DAX Measures, Relationships và business definitions đã được thống nhất:

Gross Revenue = SUM(FactSales[GrossAmount])
Net Revenue = [Gross Revenue] - [Refund Amount]
Profit = [Net Revenue] - [Cost]

Nếu mọi Report cùng dùng [Net Revenue] từ Shared Model, sửa logic một lần có thể được phản ánh trong Reports phụ thuộc. Người xây Report phải có quyền truy cập/Build phù hợp.

Trong Desktop: Home → Get data → Power BI semantic models. Có thể dùng Live Connection để sử dụng Model hiện có, không tạo bản sao Import. Khi mở rộng thành Composite Model, DirectQuery for Power BI semantic models là một khả năng khác, không hoàn toàn đồng nghĩa Live Connection.

Core-plus-specialized pattern: Core Semantic Model dùng chung KPI; specialized Reports có Layout/Filters riêng. Định nghĩa có governance tốt cũng giúp AI Consumers sử dụng cùng Business Logic.

Power BI templates (.pbit)

.pbit lưu Report Pages, Visuals, Queries, Parameters và Model Definition nhưng không chứa dữ liệu Import đã nạp. Phù hợp khi nhiều chi nhánh cần cùng bố cục nhưng Data Source/Parameters khác nhau.

File → Export → Power BI template → Save. Khi mở .pbit, người dùng cung cấp Parameters, Source Credentials và tải dữ liệu theo môi trường.

ParameterVí dụ
ServerNamesql-dev.company.local
DatabaseNameSales_North

Parameters giúp cấu hình, không phải cơ chế Security tự bảo đảm quyền truy cập.

PBIDS (.pbids)

Power BI Data Source File chứa thông tin cấu hình kết nối để Desktop biết nên kết nối Source nào. Không lưu toàn bộ Report/Measure/Credentials.

Nhu cầuTài sản
Common KPIs/RelationshipsShared Semantic Model
Same Report Structure, different sources.pbit
Standardized source connection starting point.pbids
Same KPI and LayoutShared Semantic Model + Report Template

Exam: 20 reports, same layout, different databases → PBIT; single source of truth for business metrics → Shared Semantic Model.

Unit 3 — Manage Power BI content in version control

Unit này dạy gì

Biến Report/Model thành file có thể diff, commit, branch và review; đồng bộ Git Repository với Fabric Workspace.

Power BI Desktop projects — PBIP

PBIX là file đóng gói, Git lưu phiên bản nhưng không thuận tiện diff từng Measure/Visual. Power BI Project .pbip lưu các thành phần thành thư mục/file văn bản.

Ví dụ minh họa:

SalesAnalytics/
├── SalesAnalytics.pbip
├── SalesAnalytics.SemanticModel/
│   ├── definition.pbism
│   └── definition/
│       ├── model.tmdl
│       ├── tables/
│       └── relationships.tmdl
├── SalesAnalytics.Report/
│   └── definition.pbir
└── .gitignore

TMDL (Tabular Model Definition Language): định nghĩa Model Metadata, Measures, Relationships và Tables. PBIR (Power BI Enhanced Report Format): định nghĩa Pages, Visuals/Layout dưới dạng văn bản/JSON.

Ví dụ DAX được lưu và review bằng Git Diff:

table Sales
    measure Revenue = SUM(Sales[Amount])
        formatString: "#,0.00"

Power BI Desktop → File → Save as → Power BI Project (.pbip). Tùy phiên bản có thể cần Settings/Preview Features.

Security: .gitignore không thay việc tự kiểm tra Secrets, Credentials, Tokens và dữ liệu nhạy cảm trước khi Commit.

Enable Git integration for a workspace

Fabric Git Integration hỗ trợ GitHub/Azure DevOps theo cấu hình Tenant/Capacity/Workspace và quyền Git Provider.

  1. Fabric Portal → Workspace.
  2. Workspace settings → Git integration.
  3. Chọn GitHub hoặc Azure DevOps.
  4. Authenticate.
  5. Chọn Repository/Branch/Folder.
  6. Thực hiện Initial Sync sau khi rà soát nguồn nào là authoritative.

Đừng tự động chọn giữ Git hoặc Workspace khi cả hai đã có Production Content vì có thể overwrite nội dung hợp lệ.

Work with Git-connected workspace

  • Commit: thay đổi Workspace → Git Repository.
  • Update: thay đổi Git → Workspace.
  • Branch: Feature Workflows, Pull Request, Code Review, Merge.
  • Conflict: cùng Item thay đổi ở cả Workspace và Git từ lần sync cuối. Không chỉ là lỗi Permission.

Ví dụ:

main
├── feature/revenue-fix
└── feature/new-kpi

Quy trình Resolve Conflict: kiểm tra Diff → quyết định merge/keep → validate Model → sync. Không chọn Keep Workspace/Git một cách mù quáng.

Combine projects and Git integration

PBIP local edit → Git Commit → Pull Request → Review → Merge → Fabric Development Workspace Update → Validation → Deployment.

Git Integration không mặc định triển khai Production và không tự chuyển Credentials, Data Source Bindings hay Import Data. Cần Pipeline/CI-CD riêng.

Exam: PBIP/TMDL để diff model; PBIR để diff report; Git Conflict do changes cả hai phía; Git = Source Control, không phải Stage Promotion.

Unit 4 — Manage semantic models with the XMLA endpoint

Unit này dạy gì

Sử dụng XMLA Protocol và SemPy Notebook để quản lý/kiểm tra Semantic Model bằng công cụ hoặc code có thể lặp lại.

XMLA endpoint

XMLA (XML for Analysis) là giao thức làm việc với Analysis Services engine của Power BI Semantic Models. Tools hỗ trợ đọc Metadata, chạy DAX, so sánh hoặc thay đổi Model theo quyền.

Ví dụ Workspace URL:

powerbi://api.powerbi.com/v1.0/myorg/MyWorkspace

Read-only: truy vấn/đọc. Read/write: sửa và quản lý Model trong trường hợp Capacity, Tenant Settings và Permissions hỗ trợ. XMLA không phải đường bỏ qua Security.

SemPy: inspect metadata

Fabric Notebook có sempy.fabric (API và phiên bản thực tế cần kiểm tra ở Runtime):

import sempy.fabric as fabric

model = "Sales Model"
workspace = "Sales Workspace"

tables = fabric.list_tables(model, workspace=workspace)
columns = fabric.list_columns(model, workspace=workspace)
measures = fabric.list_measures(model, workspace=workspace)

display(tables)
display(columns)
display(measures)

Dùng để kiểm tra bảng DimDate, cột cần thiết, Measure Total Revenue, tên trường trước Deployment.

Relationships and quality

relationships = fabric.list_relationships(model, workspace=workspace)
display(relationships)

Liệt kê Relationship không đủ chứng minh Foreign Keys khớp Dimension Keys. Theo ví dụ đã giảng, có thể dùng:

model_tables = {
    "DimProduct": fabric.read_table(model, "DimProduct", workspace=workspace),
    "FactSales": fabric.read_table(model, "FactSales", workspace=workspace),
}

violations = fabric.list_relationship_violations(model_tables)
display(violations)

Quan trọng: trước khi chạy cần đối chiếu đúng Signature/API của phiên bản SemPy hiện có và những Metadata cần truyền; đây là đoạn minh họa từ bài giảng, chưa được thực thi trong Runtime. Với Fact rất lớn, read_table() có thể đưa quá nhiều data về Notebook; ưu tiên Sampling hoặc Data Layer Validation phù hợp. Kiểm tra thêm Null/Unique Keys và Referential Integrity.

Evaluate measures and DAX

result = fabric.evaluate_measure(
    model,
    measure="Total Revenue",
    groupby_columns=["DimDate[Year]", "DimProduct[Category]"],
    workspace=workspace
)
display(result)
query = '''
EVALUATE
ROW("Revenue", [Total Revenue])
'''

result = fabric.evaluate_dax(model, query, workspace=workspace)
display(result)

Validation với Expected Value:

actual = float(result.iloc[0, 0])
expected = 1600.0
assert abs(actual - expected) < 0.001, f"Expected {expected}, got {actual}"

Nếu Assertion Fail, kiểm tra DAX/Filter Context/Data; không tự kết luận lỗi cú pháp. evaluate_measure thuận tiện theo Grouping, evaluate_dax linh hoạt với DAX Query bất kỳ.

External tools

Công cụChức năng
DAX StudioDAX Queries, FE/SE timings, Query Plan
Tabular EditorMetadata, Measures, Calculation Groups, BPA
ALM ToolkitSo sánh Semantic Models
SSMSQuản lý/truy vấn theo tính năng hỗ trợ
Fabric Notebook + SemPyValidation tự động, Metadata, Data Quality

BPA (Best Practice Analyzer) phát hiện các vấn đề theo rules; không thay thế kiểm thử Business Expected Values.

Exam: list_relationships() liệt kê Relationships; list_relationship_violations() hướng tới kiểm tra Orphaned Foreign Keys; evaluate_measure() kiểm tra Measure; evaluate_dax() chạy DAX Query. SemPy phù hợp Automated QA.

Unit 5 — Deploy content through stages

Unit này dạy gì

Promote Fabric/Power BI Items qua các môi trường theo quy trình, cấu hình nguồn theo Stage và tự động hóa Deployment khi cần.

Deployment pipelines

Mặc định có thể tổ chức Development → Test → Production. Fabric hỗ trợ cấu hình Pipeline 2–10 Stages trong điều kiện phù hợp.

Mỗi Stage gắn một Workspace; không tự cách ly Data Sources chỉ vì đặt tên Stage khác nhau.

StageVí dụ WorkspaceSource
DevelopmentSales-DevSales_Dev
TestSales-UATSales_UAT
ProductionSales-ProdSales_Prod

Create/configure pipeline

Fabric → Workspaces → Deployment pipelines → Create pipeline → đặt tên/chọn stages → gán Workspaces. Cần Permissions/Capacity phù hợp; Workspace không được cùng lúc gán vào Pipeline khác theo giới hạn thực tế.

Deployment rules

  • Data source rule: Source Connection thay theo môi trường khi item/connection được hỗ trợ.
  • Parameter rule: Power Query Parameter thay theo Stage. Ví dụ EnvironmentName DEV / TEST / PROD.

Rules áp dụng cho môi trường đích khi Deploy, không tự sửa nguồn. Thay Rule sau Deployment có thể cần Redeploy. Với Direct Lake: Direct Lake on SQL và Direct Lake on OneLake khác nhau về cơ chế Binding/Rules; OneLake thường dùng M Parameters/Parameter Rules phù hợp.

Compare and deploy content

Source/Target Comparison cho thấy Item New, Different, Same. Selective Deployment cho phép chọn Items thay vì mọi thay đổi. Item Pairing liên kết Items giữa stages; hai Items cùng tên không luôn tự động Pair trong mọi tình huống. Kiểm tra Relationships giữa Items, Reports và Models.

Deployment ≠ data copy: Import Model Definition thường được triển khai nhưng dữ liệu Import/Credentials không tự được copy đầy đủ; cấu hình Data Source/Gateway và Refresh khi cần. Direct Lake phải bind tới đúng Lakehouse/Warehouse ở Stage đích.

Automate deployment pipelines

Fabric REST APIs có thể dùng trong GitHub Actions, Azure DevOps hoặc tool CI/CD được cấp quyền.

Feature Branch → Pull Request → Review → Merge
→ Sync Development Workspace
→ Automated Validation
→ Deploy Test → UAT/Approval
→ Deploy Production → Post-deployment Test

Không mặc định Git Commit = tự Promote Production. Nên có Release Record, Approval và Rollback Plan cho các Model dùng chung.

Git vs Deployment Pipeline

Nhiệm vụGit IntegrationDeployment Pipeline
Version history/branch/PRCóKhông thay thế Git
Workspace syncCóMục đích khác
Dev → Test → Prod promotionKhông phải trọng tâmCó
Rules theo StageKhông thay thếCó, với Items hỗ trợ
CI/CDGit workflowsREST API/Deployment operation

Exam: Different connection in Prod → Deployment Rule; selective promotion → Selective Deployment; source history → Git; Stage Promotion → Pipeline.

Unit 6 — Maintain and monitor semantic models

Unit này dạy gì

Duy trì Data Freshness, xử lý Refresh Failures, theo dõi Dependencies và đánh giá Impact của thay đổi.

Scheduled refresh

Import Model cần Refresh dữ liệu theo lịch. Semantic Model → Settings → Scheduled refresh, cấu hình Frequency, Time Zone, Credentials, Gateway khi cần, Failure Notification. Không đặt tần suất quá cao nếu báo cáo chỉ cần daily data. SQL Server On-premises thường cần Gateway; Cloud Sources có thể không cần.

Direct Lake khác Import: Framing/metadata tham chiếu Delta version mới, không tự Import toàn bộ. Data freshness vẫn cần phối hợp thời điểm Delta được ghi xong với Model state. Không coi Direct Lake luôn real-time tuyệt đối hoặc không bao giờ cần Refresh.

Data Factory refresh orchestration

Nếu Lakehouse Load bắt đầu 05:00 nhưng lúc hoàn tất có thể là 05:30 hoặc 06:30, Scheduled Semantic Model Refresh lúc 06:00 sẽ đôi khi chạy trên dữ liệu chưa hoàn chỉnh.

Giải pháp: Fabric Data Factory Pipeline với Dependencies:

Load Lakehouse
  └─ Success → Transform/Validate
       └─ Success → Semantic model refresh
            ├─ Success → Notify success
            └─ Failure → Notify failure

Fabric → Workspace → New item → Data pipeline → thêm Activities → Semantic model refresh → chọn Workspace/Model/Connection → Success/Failure Paths → Run/Monitor. Có các tùy chọn Refresh Tables/Partitions/Retry tùy tính năng được hỗ trợ.

Monitor refresh operations

Monitoring Hub và Semantic Model Refresh History cho Status, Duration, Start/End, Errors. Một Model thường 5 phút nhưng tăng lên 18 phút cần điều tra Data Volume, Query Folding, Source, Gateway, Partitions và Capacity Throttling.

LỗiHướng xử lý
Expired credentialsUpdate Credentials
Gateway unavailableCheck Gateway Service
TimeoutSource Query/Network
Source schema changedData Types/Power Query
Capacity throttlingCapacity Metrics/Workload
Upstream data incompleteData Pipeline Dependencies

Lineage view and impact analysis

Lineage: Source → Lakehouse → Semantic Model → Reports. Nếu Report cũ dữ liệu, xem Last Refresh và Upstream Pipeline. Impact Analysis giúp nhận diện Reports/Items bị ảnh hưởng khi đổi hoặc xóa Column/Measure. Trước Schema Change: tìm dependencies → kiểm thử Test Stage → báo Report Owners → có kế hoạch Rollback.

Endorsement hỗ trợ Governance/trust nhưng không thay Security, Refresh hay Validation.

Exam: Import freshness → Scheduled Refresh; upstream job variable duration → Data Factory Dependency; Refresh failure → Monitoring Hub/History; change column → Impact Analysis.

Unit 7 — Exercise: Manage semantic models through their lifecycle

Unit này dạy gì

Chuẩn bị

Bước 1 — Tạo Import Semantic Model mẫu

Desktop → Modeling → New table:

FactSales =
DATATABLE(
    "SalesID", INTEGER,
    "RegionKey", INTEGER,
    "Revenue", INTEGER,
    {
        {101,1,100},{102,1,200},
        {103,2,150},{104,2,250},
        {105,3,400},{106,3,500}
    }
)

DimRegion =
DATATABLE(
    "RegionKey", INTEGER,
    "RegionName", STRING,
    {{1,"North"},{2,"Central"},{3,"South"}}
)

Relationship: DimRegion[RegionKey] (1) → FactSales[RegionKey] (*), Single Active. Measure:

Total Revenue = SUM(FactSales[Revenue])

Kết quả North 300, Central 400, South 900, Total 1600. Lưu DP600-Lifecycle.pbix và Publish vào DP600-Lifecycle-Dev.

Bước 2 — Fabric Notebook và SemPy

Workspace → New item → Notebook → NB-Validate-Semantic-Model.

import sempy.fabric as fabric
WORKSPACE = "DP600-Lifecycle-Dev"
MODEL = "DP600-Lifecycle"

Nếu không import được SemPy, kiểm tra Fabric Runtime/Package Availability.

Bước 3 — Validate model metadata

tables = fabric.list_tables(MODEL, workspace=WORKSPACE)
columns = fabric.list_columns(MODEL, workspace=WORKSPACE)
measures = fabric.list_measures(MODEL, workspace=WORKSPACE)

display(tables)
display(columns)
display(measures)

assert "Total Revenue" in measures["Name"].tolist(), "Missing Total Revenue"

Expected: FactSales, DimRegion, Total Revenue. Nếu Assertion fail, không Promote.

Bước 4 — Relationships, Data Quality

relationships = fabric.list_relationships(MODEL, workspace=WORKSPACE)
display(relationships)

model_tables = {
    "DimRegion": fabric.read_table(MODEL, "DimRegion", workspace=WORKSPACE),
    "FactSales": fabric.read_table(MODEL, "FactSales", workspace=WORKSPACE),
}

violations = fabric.list_relationship_violations(model_tables)
display(violations)

dim = model_tables["DimRegion"]
assert dim["RegionKey"].isnull().sum() == 0
assert dim["RegionKey"].duplicated().sum() == 0

Lưu ý: Đối chiếu chữ ký hàm và schema DataFrame với SemPy Runtime hiện tại trước khi chạy; code trên được trích lại từ bài giảng, chưa chạy trong Tenant người học. Kết quả kỳ vọng: không có orphaned keys; Dimension Key unique và not null.

Bước 5 — Validate Business Measure

query = '''
EVALUATE
ROW("TotalRevenue", [Total Revenue])
'''

result = fabric.evaluate_dax(MODEL, query, workspace=WORKSPACE)
display(result)

actual = float(result.iloc[0, 0])
expected = 1600.0
assert abs(actual - expected) < 0.001, f"Revenue mismatch: {actual}"
print("Validation passed")

Message Validation passed chỉ xuất hiện nếu thật sự chạy và đạt; đây không phải xác nhận đã chạy thực tế.

Unit 8 — Module assessment

Câu 1 — Same visuals/measures/layout, different databases: A .pbit; B .pbids; C Shared Model DirectQuery. Đáp án A. PBIT chứa cấu trúc Report/Model/Parameters nhưng không nạp dữ liệu; PBIDS chỉ kết nối nguồn; Shared Model không giải quyết trực tiếp việc tạo lại toàn bộ Report Template với nguồn riêng.

Câu 2 — Git Conflict: A Item đổi cả Workspace và Repository từ lần sync cuối; B Item chỉ ở Workspace; C Git Provider thiếu Permission. Đáp án A. B là khác biệt/Pending Change, C là Authentication/Authorization issue.

Câu 3 — Kiểm tra orphaned foreign keys: A list_relationship_violations(); B list_relationships(); C evaluate_measure(). Đáp án A. B chỉ liệt kê relationships, C tính Measure.

Câu 4 — Production phải dùng live database: A Data Source Deployment Rule; B sửa thủ công mỗi lần; C hardcode model riêng từng Stage. Đáp án A với loại source hỗ trợ; các phương án còn lại tăng manual errors/maintenance.

Câu 5 — Lakehouse Load có thể lâu hơn 1 giờ: A Data Factory Pipeline refresh Model sau Success; B chờ cứng 2 giờ; C bật “real-time refresh” chung. Đáp án A. Dựa vào dependency completion, không dựa vào thời gian cố định.

Kiến thức liên kết xuyên suốt

  1. Business Logic: hiểu Row Context, Filter Context, Grain và DAX để tạo Measures đúng.
  2. Architecture: Star Schema và Storage Mode xác định nền tảng truy vấn, quản trị và Scale.
  3. Performance: đo trước khi sửa; không hy sinh KPI Correctness để tăng tốc.
  4. Security: RLS giới hạn Rows, OLS giới hạn Objects; danh tính và Workspace Permissions quyết định việc thực thi.
  5. ALM: Git quản lý phiên bản, SemPy/XMLA kiểm thử, Deployment Pipelines Promote, Monitoring quản lý Production.

Bẫy Scenario cần ưu tiên ôn

  • Calculated Column vs Measure; SUM vs SUMX; AVERAGEX(VALUES(...)) theo Grain.
  • Direct Lake on OneLake vs Direct Lake on SQL; không đồng nhất fallback.
  • USERELATIONSHIP vs Role-playing Dimension.
  • HASONEVALUE vs ISINSCOPE; FILTER vs KEEPFILTERS.
  • Calculation Group vs Aggregation Table (logic reuse vs data summary optimization).
  • Query Scaleout vs Large Model vs XMLA vs OneLake Integration.
  • RLS vs OLS, Report Filters/Hide Columns không phải Security.
  • Multiple RLS Roles thường là Union; Admin/Member/Contributor không dùng RLS như Viewer.
  • Git Integration vs Deployment Pipeline; Deployment không tự copy Import Data/Credentials.
  • list_relationships vs list_relationship_violations vs evaluate_measure vs evaluate_dax.
  • Scheduled Refresh theo giờ cố định vs Data Factory Dependency theo hoàn thành Upstream.
