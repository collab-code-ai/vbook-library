Unit 1 — Introduction

Unit này dạy gì

Chẩn đoán trước khi tối ưu. Một Report 30 giây có thể chậm do DAX, Data Model, Visual Rendering, DirectQuery Source, Network hoặc concurrency. Tăng Capacity mà chưa xác định bottleneck có thể lãng phí.

Nội dung chính trong unit

Ví dụ FactSales 50 triệu dòng, 20 Reports, 200 users, AI Consumers bị timeout. Trước tiên cần đo từng Visual, phân loại thời gian. Chu trình bắt buộc:

Measure baseline -> Diagnose root cause -> Apply targeted fix -> Measure again

Sau tối ưu phải bảo đảm kết quả nghiệp vụ không đổi trong cùng Filter Context. DAX nhanh hơn nhưng KPI sai không phải cải thiện thành công.

Unit 2 — Use Performance analyzer to diagnose issues

Unit này dạy gì

Dùng Performance analyzer của Power BI Desktop/Service để tách thành phần thời gian của từng Visual và lấy DAX Query để phân tích.

Open Performance analyzer

Desktop: Report view → Optimize → Performance analyzer. Service: Edit → View → Performance analyzer (tùy UI/quyền). Công cụ đo chứ không tự tối ưu.

Record and measure performance

  1. Mở Report và Performance analyzer.
  2. Chọn Start recording.
  3. Chọn Refresh visuals hoặc thực hiện Filter/Slicer thường dùng.
  4. Mở rộng từng Visual, ghi Timing Breakdown.
  5. Stop; Export JSON khi cần lưu baseline.
  6. Phân biệt Initial Page Load và User Interaction.

Nên so sánh cold-cache và warm-cache khi cần, kiểm soát tải môi trường và đo lặp nhiều lần.

Timing metrics

MetricDiễn giảiHướng điều tra
DAX queryTruy vấn Semantic ModelMeasure, Filter, Relationships, Model

Direct queryThực thi truy vấn Source trong DirectQuerySQL, source, network

Ví dụ Product Detail: DAX 4500 ms, Display 300 ms; KPI Card: DAX 50 ms, Display 30 ms. Nên tập trung điều tra DAX Query của Product Detail trước, không bắt đầu bằng đổi màu Visual.

Export and analyze DAX queries

Performance analyzer → Expand slow visual → Copy query hoặc Run in DAX query view khi UI hỗ trợ. Truy vấn do Visual sinh ra có thể gồm SUMMARIZECOLUMNS, TOPN, Filters, VAR, ORDER BY và nhiều Measures. Nó khác Measure Definition.

EVALUATE
SUMMARIZECOLUMNS(
    DimProduct[Category],
    "Revenue", [Revenue]
)

Ở Service, có thể cần Copy Query rồi mở DAX Query View riêng thay vì chạy trực tiếp.

DAX Studio diagnostics

  • Server Timings: Formula Engine (FE) vs Storage Engine (SE).
  • Query Plan: Logical và Physical Plan.
  • Model Metrics / VertiPaq Analyzer: kích thước bảng/cột, cardinality, compression, relationships.

FE thường xử lý DAX logic/điều phối; SE thực hiện truy xuất/tổng hợp dữ liệu hiệu quả theo storage. Phải xem số đo, không kết luận bottleneck chỉ từ tên hàm.

Interpret results và best practices

Ưu tiên Visual ảnh hưởng người dùng nhiều nhất, thay đổi từng yếu tố, dùng dataset tương đương Production, ghi Before/After và kiểm tra correctness. Ví dụ từ 4500 ms DAX xuống 1300 ms là một tín hiệu tốt nếu trong điều kiện tương đương; nhưng không được coi là kết quả đã đo trên môi trường thực của người học.

Exam: slowest visual → Performance analyzer; FE/SE timings → DAX Studio; display dominates → Visual Optimization; DAX dominates → DAX/Model.

Unit 3 — Optimize DAX calculations

Unit này dạy gì

Viết lại DAX để giảm biểu thức lặp, lọc hợp lý và kiểm soát tính toán theo Grain mà không đổi kết quả nghiệp vụ.

Variables to eliminate repeated calculations

Trước:

Sales YoY Growth % =
DIVIDE(
    [Sales] - CALCULATE([Sales], PARALLELPERIOD('Date'[Date], -12, MONTH)),
    CALCULATE([Sales], PARALLELPERIOD('Date'[Date], -12, MONTH))
)

Sau:

Sales YoY Growth % =
VAR SalesPriorYear =
    CALCULATE([Sales], PARALLELPERIOD('Date'[Date], -12, MONTH))
RETURN DIVIDE([Sales] - SalesPriorYear, SalesPriorYear)

VAR tăng readability và có thể giảm tính lại kết quả trong cùng Context. Engine có thể tự tối ưu biểu thức lặp; không cam kết luôn nhanh hơn. VAR được đánh giá theo Context tại nơi định nghĩa nên di chuyển biến sai chỗ có thể đổi nghĩa.

FILTER vs KEEPFILTERS

-- Filter a whole fact table
High Value Sales =
CALCULATE([Total Sales], FILTER(Sales, Sales[Amount] > 1000))

-- Column Boolean filter
High Value Sales =
CALCULATE([Total Sales], Sales[Amount] > 1000)

Boolean Column Filter đơn giản thường dễ tối ưu hơn duyệt toàn Fact, nhưng phải giữ đúng semantics. Khi đang có Filter trên cùng Column, CALCULATE có thể ghi đè filter hiện tại; KEEPFILTERS lấy phép giao:

Online Sales =
CALCULATE([Total Sales], KEEPFILTERS(Sales[Channel] = "Online"))

Nếu slicer đang chọn Retail, Retail ∩ Online thường không có dòng. Không KEEPFILTERS có thể thay Retail bằng Online. KEEPFILTERS là công cụ điều chỉnh Filter Context, không phải “FILTER nhanh hơn” một cách tuyệt đối.

Iterator costs

Revenue = SUMX(Sales, Sales[Quantity] * Sales[UnitPrice])
-- Nếu đã có cột LineTotal đúng nghiệp vụ:
Revenue = SUM(Sales[LineTotal])

Iterator hữu ích khi cần biểu thức row-by-row. Cột tính sẵn có thể giúp phép tổng hợp đơn giản nhưng làm tăng Storage/ETL; chỉ chọn sau khi đo và xét Grain.

Avoid expensive patterns

-- Pattern cần đánh giá
Large Orders = COUNTROWS(FILTER(Sales, Sales[Amount] > 1000))

-- Viết lại điều kiện lọc cột
Large Orders = CALCULATE(COUNTROWS(Sales), Sales[Amount] > 1000)

Nested CALCULATE không luôn xấu, nhưng Filter Context nhiều tầng khó kiểm tra. Dùng VAR, tách Measures và loại logic không cần. Tránh REMOVEFILTERS() quá rộng nếu chỉ muốn bỏ Region:

Pct of Region Total =
DIVIDE(
    [Total Sales],
    CALCULATE([Total Sales], REMOVEFILTERS(DimRegion))
)

REMOVEFILTERS() không tham số và REMOVEFILTERS(DimRegion) khác nghĩa; không được tối ưu bằng cách làm KPI sai.

Move calculations to data layer

Biến đổi tĩnh như FullName, Date Part hoặc Normalized Code có thể làm ở SQL View, Power Query, Dataflow Gen2 hoặc Notebook. Có thể giảm tính toán trong Model, nhưng vẫn tốn ETL, Storage và có thể ảnh hưởng Query Folding. KPI động theo Slicer thường là Measure.

AI experience

Copilot/Fabric Data Agents có thể tạo DAX Query trên cùng Semantic Model. Measure đắt đỏ gây timeout; Measure không rõ nghĩa gây kết quả sai. Cần tối ưu cả Performance, Description và Correctness.

Exam: repeated expression → VAR; large FILTER table → Boolean Column Filter khi tương đương; preserve filter → KEEPFILTERS; static transformation → upstream; dynamic KPI → Measure.

Unit 4 — Reduce cardinality for better performance

Unit này dạy gì

Giảm lượng dữ liệu phải lưu, nén và xử lý bằng cách quản lý số giá trị phân biệt của Column.

Cardinality

Cardinality = số distinct values trong cột. Ví dụ 1M rows: Region = 5, Category = 20, ProductKey = 10.000, TransactionID ≈ 1M, EventTimestamp ≈ 999.850. High-cardinality Text/GUID/Timestamp thường khó nén hơn cột ít giá trị; kiểu dữ liệu và thứ tự dòng cũng ảnh hưởng.

Identify high-cardinality columns

  • GUID/Surrogate Keys không sử dụng.
  • Timestamp có mili giây nhưng chỉ báo cáo ngày.
  • Free-text descriptions dài.
  • Invoice/Order/Session IDs gần như duy nhất.

Không xóa một khóa chỉ vì không thấy trên Visual: nó có thể cần cho Relationship, RLS, Drillthrough hoặc downstream dependencies.

Reduction strategies

  1. Vertical filtering: loại những cột không dùng; giảm size và các field gây nhiễu.
  2. Reduce time precision: DateTime milliseconds → Date nếu không cần giờ/phút. Nếu giữ cả cột gốc và cột Date mới thì có thể chưa giảm dung lượng.
  3. Bucket continuous values: Age Band, Amount Band; giữ cột gốc nếu Measure cần giá trị chính xác.
  4. Horizontal filtering: loại rows không cần thiết (ví dụ lịch sử 2010–2022 không phục vụ báo cáo), có cân nhắc compliance/history.
  5. Optimize data types: Integer Keys, Date, Currency/Decimal hợp lý. Không làm mất leading zeros có nghĩa, tràn kiểu hoặc tạo duplicate keys.

Trade-offs

Thay đổiLợi íchRủi ro
Timestamp → DateÍt distinct valuesMất phân tích theo giờ
Age → Age BandDễ nhómMất tuổi chính xác
Remove TransactionIDModel nhẹMất Drillthrough
Filter historical rowsÍt dữ liệuMất phân tích nhiều năm

Exam: high precision timestamp, daily report only → Date; unused GUID → remove; unnecessary columns → Vertical; unnecessary rows → Horizontal.

Unit 5 — Implement aggregations

Unit này dạy gì

Sử dụng Summary Tables để phục vụ các truy vấn phổ biến ở Grain cao hơn Detail Fact.

When aggregations help

FactSales 500M rows nhưng Executive Dashboard chỉ cần Revenue by Month/Region. AggSalesMonthRegion có vài nghìn dòng và có thể trả lời những truy vấn phù hợp. Nó không tự trả lời chính xác Revenue by Customer nếu không có CustomerKey.

User-defined aggregations

Tạo bảng bằng SQL/Power Query/Warehouse:

SELECT MonthKey, RegionKey,
       SUM(SalesAmount) AS TotalSales,
       COUNT(*) AS SalesRows
FROM FactSales
GROUP BY MonthKey, RegionKey;

Dùng Manage aggregations để mapping Column/Function từ Aggregation tới Detail Table:

Agg ColumnFunctionDetail
TotalSalesSumFactSales[SalesAmount]
SalesRowsCount table rowsFactSales
MonthKeyGroupByFactSales[MonthKey]
RegionKeyGroupByFactSales[RegionKey]

Các Mapping Functions gồm Sum, Count, Count table rows, Min, Max, GroupBy khi được hỗ trợ. Ẩn Agg Table để người dùng query qua Fact/Measures. Kiến trúc phổ biến: Agg Import, Detail DirectQuery, Dimensions Import/Dual. Engine chỉ dùng Agg khi truy vấn và mapping đáp ứng quy tắc. RLS phải nhất quán giữa đường Aggregate và Detail.

Automatic aggregations

Automatic Aggregations sử dụng Query Patterns/Logs để huấn luyện và quản lý Aggregation Cache khi Capacity, nguồn DirectQuery và cấu hình được hỗ trợ. Có thể bật Training/Schedule trong Semantic Model Settings. Khác User-defined: system chọn cache theo workload, Developer không mapping thủ công mọi bảng. Không phải mọi SKU/Connector hỗ trợ.

Monitor effectiveness

Kiểm tra Training/Refresh History, Azure Log Analytics khi đã cấu hình, Aggregation Hit Rate, tỷ lệ quay về Detail Query, thời gian before/after, memory/cache và mapping/grain. Nếu báo cáo vẫn chậm, đừng mặc định Aggregation đã được dùng.

Direct Lake

Direct Lake đã tối ưu truy cập Delta Columns. Chỉ xây Delta Summary Table khi benchmark chứng minh cần thiết. Một Delta Summary Table không tự tương đương User-defined Aggregation Mapping của Import/DirectQuery.

Exam: billions of DirectQuery fact rows + repeated summaries → Aggregations; well-known query grain → User-defined; patterns vary and supported capacity → Automatic; slow despite aggregation → mapping/grain/hits.

Unit 6 — Troubleshoot common performance issues

Unit này dạy gì

Xây quy trình điều tra hệ thống: Visual → DAX → Relationships/Model → Source → Test lại.

Systematic workflow

Slow Report
   ↓
Performance analyzer
   ├── DAX query → DAX Query View / DAX Studio / Model
   ├── Visual display → data points / visual complexity
   ├── DirectQuery → source execution / folding / network
   └── Other → scheduling / concurrency
   ↓
Targeted fix → Compare baseline → Verify business results

Best Practice Analyzer (BPA)

BPA kiểm tra rules về Performance, DAX Expressions, Error Prevention, Maintenance và Formatting. Có thể sử dụng Tabular Editor/BPA hoặc Fabric Sample Notebooks; Model Memory Analyzer đánh giá Memory by Tables/Columns/Partitions/Relationships. Cảnh báo là gợi ý chứ không phải mọi rule đều phải được sửa.

Complex visuals

  • Too many Measures trong một Table có thể tăng công việc của engine.
  • Scatter Chart với quá nhiều Points tăng Rendering.
  • 30 Visuals trên một trang tạo nhiều Queries/overhead. Microsoft Learn gợi ý khoảng tám Visuals như một guideline chứ không là hard limit.
  • Cân nhắc Top N, Drillthrough, aggregation, chia trang.

Relationships and filter context

Kiểm tra Ambiguous Paths, Both Direction không cần thiết, Large Bridge Tables, High-cardinality Relationship Keys. REMOVEFILTERS() quá rộng có thể làm sai Percentage of Total. USERELATIONSHIP phù hợp cho quan hệ khác được định nghĩa, trong giới hạn security.

DirectQuery

Kiểm tra Source SQL/Execution Plan, Index/Partition, Query Folding, Network Round Trips, Gateway và Source Capacity. Dùng Summary Import/Aggregations nếu kiến trúc phù hợp.

Checklist

  1. Đo từng Visual và ghi Baseline.
  2. Phân loại DAX, Visual Display, DirectQuery, Other.
  3. Copy DAX Query và kiểm tra Server Timings/Query Plan.
  4. Rà soát DAX/Filter Context.
  5. Rà soát Cardinality, Column Size, Data Types.
  6. Kiểm tra Relationships, số Visual/Data Points.
  7. Nếu DirectQuery: Source Query/Folding/Network.
  8. Sửa một yếu tố, đo lại và đối chiếu KPI.

Unit 7 — Exercise: Diagnose and fix a slow report

Unit này dạy gì

Đo Report, tối ưu Measure và Cardinality, kiểm tra tốc độ và tính đúng đắn. Bài dưới là Lab tự biên soạn theo mục tiêu công khai, không phải log chạy thật hoặc bản sao Hosted Lab.

Chuẩn bị

Power BI Desktop Windows; không cần Capacity trả phí nếu làm local. Nếu dùng Fabric Workspace, cần quyền và License phù hợp. Dataset 120.000 dòng minh họa, không đảm bảo benchmark thấy khác biệt lớn.

Tạo Power Query Sales

Power BI Desktop → Transform data → New Source → Blank Query → Advanced Editor:

let
    Source = Table.FromList(List.Numbers(1, 120000), Splitter.SplitByNothing(), {"RowId"}),
    Typed = Table.TransformColumnTypes(Source, {{"RowId", Int64.Type}}),
    AddOrderDate = Table.AddColumn(
        Typed, "OrderDate",
        each Date.AddDays(#date(2025, 1, 1), Number.Mod([RowId], 730)),
        type date
    ),
    AddTimestamp = Table.AddColumn(
        AddOrderDate, "EventTimestamp",
        each #datetime(2025, 1, 1, 0, 0, 0) + #duration(0, 0, 0, [RowId] / 1000),
        type datetime
    ),
    AddRegion = Table.AddColumn(
        AddTimestamp, "Region", each if Number.Mod([RowId], 2) = 0 then "North" else "South", type text
    ),
    AddProduct = Table.AddColumn(
        AddRegion, "ProductKey", each Number.Mod([RowId], 200) + 1, Int64.Type
    ),
    AddQuantity = Table.AddColumn(
        AddProduct, "Quantity", each Number.Mod([RowId], 5) + 1, Int64.Type
    ),
    AddPrice = Table.AddColumn(
        AddQuantity, "UnitPrice", each 10 + Number.Mod([RowId], 40), Currency.Type
    ),
    AddAmount = Table.AddColumn(
        AddPrice, "Amount", each [Quantity] * [UnitPrice], Currency.Type
    )
in
    AddAmount

Close & Apply. Tạo Date Table, Relationship và Measure:

Date = CALENDAR(DATE(2025, 1, 1), DATE(2026, 12, 31))
YearMonth = FORMAT('Date'[Date], "yyyy-MM")
Revenue = SUM(Sales[Amount])

Date[Date] (1) → Sales[OrderDate] (*).

Before vs After DAX

High Value Revenue Before =
SUMX(FILTER(Sales, Sales[Amount] > 100), Sales[Amount])

High Value Revenue After =
CALCULATE([Revenue], KEEPFILTERS(Sales[Amount] > 100))

Và YoY:

YoY Growth Before =
DIVIDE(
    [Revenue] - CALCULATE([Revenue], DATEADD('Date'[Date], -1, YEAR)),
    CALCULATE([Revenue], DATEADD('Date'[Date], -1, YEAR))
)

YoY Growth After =
VAR RevenuePriorYear =
    CALCULATE([Revenue], DATEADD('Date'[Date], -1, YEAR))
RETURN DIVIDE([Revenue] - RevenuePriorYear, RevenuePriorYear)

Đo và xác nhận

  1. Tạo Table Date[YearMonth], Sales[Region], hai Before Measures.
  2. Optimize → Performance analyzer → Start recording → Refresh visuals.
  3. Ghi DAX Query, Display, Total và lưu query.
  4. Đo lại với hai After Measures trong điều kiện tương đương; tránh benchmark hai Visual đồng thời.
  5. Kiểm tra kết quả Before và After bằng nhau ở mọi Filter Context dùng thử.
  6. Dùng Model Metrics tìm Column EventTimestamp có Cardinality cao; nếu không dùng, Remove trong Power Query → Close & Apply → đo Model Size lại.
  7. Lưu PBIX, ví dụ DP600-Performance-Lab.pbix.

Lỗi và interpretation

  • YoY trả BLANK: có thể không có dữ liệu năm trước.
  • Before/After gần bằng nhau: engine đã tối ưu hoặc dataset quá nhỏ/cache ảnh hưởng.
  • Remove Timestamp giảm Model Size nhưng chưa chắc DAX Query Time giảm đáng kể.
  • Nếu kết quả KPI khác nhau: phải sửa semantics, không được coi là tối ưu thành công.

Unit 8 — Knowledge check

Câu 1 — DAX query 4200 ms, display 150 ms: A Rendering; B Measures/DAX Filter Patterns; C Network. Đáp án B. DAX chiếm phần lớn; A/C không là ưu tiên theo số đo.

Câu 2 — CALCULATE lặp ba lần: A thay tất cả Iterators; B lưu bằng VAR; C Power Query Column. Đáp án B. Tái sử dụng biểu thức trong Context; không tự chuyển KPI động thành cột tĩnh.

Câu 3 — Timestamp mili giây nhưng chỉ phân tích ngày: A xóa không thay; B đổi Text; C giảm precision thành Date trong Power Query. Đáp án C. Giữ thông tin ngày và giảm distinct values.

Câu 4 — DirectQuery Fact hàng tỷ dòng, summary Month/Region: A Aggregations; B thêm FILTER; C chuyển mọi Dimension DirectQuery. Đáp án A. Summary Grain phù hợp giảm truy vấn Detail.

Câu 5 — 25 Visuals, mỗi DAX dưới 200 ms, trang tải hơn 10 giây: A mọi Measure đều sai; B Visual Count và overhead; C chắc chắn do Cardinality. Đáp án B. Tập trung Page Design, Rendering, Concurrency.
