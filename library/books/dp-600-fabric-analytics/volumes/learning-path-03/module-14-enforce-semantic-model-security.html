Unit 1 — Introduction

Unit này dạy gì

Phân biệt bảo vệ dữ liệu với Report Filtering. Một Semantic Model duy nhất phục vụ North/Central/South Managers nhưng mỗi người chỉ xem vùng của mình, đồng thời Salary/PersonalAddress không được lộ cho người không thuộc HR.

Nội dung chính trong unit

  • RLS (Row-Level Security): giới hạn những hàng dữ liệu theo User/Role. Ví dụ North Manager chỉ thấy FactSales[Region] = North.
  • OLS (Object-Level Security): giới hạn truy cập Table/Column. Ví dụ Salary Column chỉ cho HR.
  • Report/Slicer Filter: hỗ trợ trải nghiệm phân tích; không thay thế RLS/OLS tại Semantic Model.

Nếu Copilot/Data Agent truy vấn Semantic Model dưới danh tính người dùng cuối và Security Context được truyền đúng, các giới hạn RLS/OLS phải được tôn trọng. Với Shared Technical Account/Service Principal, cần xem xét Effective Identity; không mặc định agent tự hiểu quyền người hỏi.

Unit 2 — Implement row-level security

Unit này dạy gì

Sử dụng DAX Rules, Roles và Security Mapping để lọc dữ liệu đúng người; phân biệt Static và Dynamic RLS, triển khai SSO/DirectQuery, tối ưu hiệu năng.

RLS and star schemas

Ví dụ:

DimRegion(RegionKey, RegionName) [1] → [*] FactSales(RegionKey, Revenue)

Role trên DimRegion:

[RegionName] = "North"

Với FactSales có North: 100+200, Central:300, South:400, North Manager chỉ nhận Revenue 300 nếu Active Relationship truyền filter chính xác. Lọc Dimension nhỏ thường phù hợp hơn kiểm tra phức tạp trên từng Fact Row lớn.

Create security roles

Desktop → Modeling → Manage roles → New → đặt North_Sales → chọn DimRegion và biểu thức [RegionName] = "North" → Save. Định nghĩa Role trong Model khác với gán Role Members ở Service sau Publish.

FALSE() trên bảng trong một Role có thể chặn mọi dòng của bảng đó, nhưng không phải cách ẩn Column Metadata. Nếu một Role không định nghĩa filter, nó không tự giới hạn dữ liệu; cần cẩn trọng khi User thuộc nhiều Roles.

Dynamic security with USERPRINCIPALNAME()

[UserUPN] = USERPRINCIPALNAME()

UPN là User Principal Name của danh tính đang truy vấn, thường giống email nhưng không bắt buộc trùng email chính. Dynamic RLS thay Role Per Region bằng logic định nghĩa chung và Data Mapping thay đổi được.

Security mapping table pattern

Ví dụ UserRegionAccess:

UserUPNRegionKey
alice@example.com1
alice@example.com2
bob@example.com3
carol@example.com1

Đặt RLS Filter trên DimRegion:

CONTAINS(
    UserRegionAccess,
    UserRegionAccess[UserUPN], USERPRINCIPALNAME(),
    UserRegionAccess[RegionKey], DimRegion[RegionKey]
)

Alice thấy Regions 1 và 2. User không có Mapping trả FALSE ở mọi Region — Fail Closed. Ở thiết kế này Mapping Table được dùng như bảng tra cứu độc lập; khi triển khai Mapping qua Relationships, cần kiểm tra Security Filter Propagation, Cardinality và Both Direction.

Biểu thức nguy hiểm:

IF(USERPRINCIPALNAME() = "alice@example.com", [RegionName] = "North", TRUE())

Mọi User khác Alice được TRUE và có thể xem dữ liệu không được phép. Không mặc định cấp toàn quyền cho danh tính không khớp.

Static RLS

Role North_Sales: [RegionName]="North"; Role South_Sales: [RegionName]="South". Phù hợp ít nhóm, ít thay đổi; khó bảo trì nếu Users thường đổi Region hoặc một Manager phụ trách nhiều Region.

USERNAME vs USERPRINCIPALNAME

Desktop, USERNAME() có thể là DOMAIN\user; Service thường dùng UPN. USERPRINCIPALNAME() phù hợp hơn để map danh tính Microsoft Entra, nhưng trong B2B Guest có thể có biến thể #EXT#. Nên tạo Measure kiểm tra:

Current Identity = USERPRINCIPALNAME()

Kiểm tra bằng tài khoản Viewer thực, đặc biệt B2B/Cross-tenant. Không mặc định địa chỉ Email nhân sự bằng Entra UPN.

DirectQuery with SSO

DirectQuery Source có SSO có thể nhận danh tính người cuối và thực thi Source-side RLS; phụ thuộc connector, authentication và cấu hình hỗ trợ. Import không tự kế thừa Source RLS. DirectQuery không đồng nghĩa SSO được bật mặc định.

RLS performance

Ưu tiên lọc Dimensions, Relationship Paths hợp lệ, Mapping Table có Grain/Keys hợp lý; tránh Lookups phức tạp lặp trên Fact lớn. Đo bằng Performance analyzer và kiểm thử Security với dữ liệu quy mô thực tế.

Exam: Dynamic UPN + Mapping cho Users thay đổi quyền; USERPRINCIPALNAME() cho identity; Fail Closed khi không match; RLS trên Dimension cho Star Schema.

Unit 3 — Apply object-level security

Unit này dạy gì

Bảo vệ Tables/Columns nhạy cảm, hiểu khác biệt giữa OLS và Hide in report view, công cụ cấu hình và các giới hạn.

When to use OLS

Employee(Name, Department, Salary, PersonalAddress): Sales Manager có thể xem Name/Department nhưng không xem Salary/PersonalAddress. RLS không thể ẩn một Column trên mọi hàng; dùng OLS.

Hide in report view chỉ ẩn trong Fields Pane, không phải Security Boundary. OLS None ngăn truy cập đối tượng và hạn chế metadata tương ứng.

Configure OLS with Tabular Editor

  1. Desktop → Manage roles → tạo General_Manager.
  2. External tools → Tabular Editor.
  3. Mở Role/Table Permissions, chọn Employee[Salary].
  4. Đặt Metadata Permission = None (không Read).
  5. Save/Publish, gán Members và Test.

Cập nhật quan trọng: Tài liệu Microsoft mới có thêm cấu hình OLS bằng TMDL View, không chỉ Tabular Editor. Ví dụ minh họa:

createOrReplace

    role General_Manager
        modelPermission: read

        tablePermission Employee
            columnPermission Salary
                metadataPermission: none

TMDL cần Preview/Apply/Publish và kiểm thử trong môi trường hỗ trợ.

Hide entire tables / columns

Có thể đặt None cho cả Payroll/SalaryBand Tables hoặc riêng Employee[Salary], Customer[NationalID], Finance[InternalCost]. Nếu Hide Table có Relationship/Measures phụ thuộc, cần kiểm tra các dependencies để tránh Visual errors.

OLS limitations

  • OLS chủ yếu cho Tables/Columns, không phải một công tắc bảo vệ Measure độc lập.
  • Measure sử dụng Column bị OLS từ chối có thể không truy vấn được.
  • Admin/Member/Contributor có quyền chỉnh sửa thường không bị OLS/RLS giới hạn theo cách của Viewer.
  • Một số tính năng như Quick Insights, Smart Narrative và Excel Data Types Gallery có hạn chế với OLS.
  • Visual tham chiếu Column bị OLS chặn có thể hiển thị lỗi field not found.

Combine OLS and RLS

North Manager: RLS = North, OLS = Salary None. HR Payroll: được cấp quyền Salary trong phạm vi nghiệp vụ. Không ghép các Role riêng biệt một cách tùy tiện: Analysis Services có giới hạn về phối hợp RLS từ một Role và OLS từ Role khác. Thiết kế Role phù hợp và kiểm thử quyền hợp nhất bằng danh tính thực.

Exam: restrict rows → RLS; sensitive columns/tables → OLS; hide field for usability ≠ security; OLS Read vs None.

Unit 4 — Test security and manage roles

Unit này dạy gì

Kiểm thử Roles trên Desktop và Service; gán thành viên; phân biệt Model Security và Workspace Permissions; tránh lỗi nhiều Role và Guests.

Test on Desktop

Modeling → View as → chọn Role → Other user để thử Dynamic RLS → kiểm tra Table, KPI Cards, Total Row, Slicers, Drillthrough và Measures → Stop viewing.

Ví dụ Mapping: Alice = North, Bob = South, Carol = North+Central. Kỳ vọng tất cả Visual và Measures đều có Data Scope đúng, không chỉ một Table.

Test in Service

Workspace → Semantic Model → More options (...) → Security → Test as role. Chú ý Test as role không hoàn toàn mô phỏng authentication của Guest, Embedded/SSO. Nên kiểm thử End-to-end bằng Viewer thực.

Assign role membership

Role Definitions được Publish từ Model; Role Membership cấu hình trong Semantic Model Security của Service. Có thể gán Individuals, Microsoft Entra Security Groups và các nhóm Mail/Distribution được hỗ trợ. Microsoft 365 Groups không hỗ trợ trực tiếp cho RLS Role Membership. Tài liệu chuyên sâu hiện tại không cho thêm Service Principal trực tiếp như người dùng cuối vào RLS Role; Embedded cần cơ chế Effective Identity phù hợp.

Entra Groups for scalable management

GroupRole
PBI-Sales-NorthNorth_Sales
PBI-Sales-SouthSouth_Sales
PBI-Sales-CentralCentral_Sales

Với 200 users/5 Regions, quản lý Groups hiệu quả hơn gán từng User. Phân biệt Static RLS + Group Membership (logic cố định, Members đổi) với Dynamic RLS + Mapping Table (một Role, quyền từng User từ dữ liệu). B2B Guests cần kiểm tra UPN/Group Membership thực tế.

Workspace Roles and RLS

Workspace RoleRLS áp dụng như với người chỉ đọc?
AdminKhông
MemberKhông
ContributorKhông
ViewerCó, khi RLS được cấu hình/áp dụng phù hợp

Ngoài Workspace Roles còn có Read, Build, Write Permissions. Viewer + Build vẫn có thể chịu RLS; không cấp Contributor chỉ để User tự tạo Report nếu quyền Build đáp ứng nhu cầu.

Multiple roles and common mistakes

RLS Roles được hợp nhất theo union: nếu Alice thuộc North Role và South Role, có thể xem cả North+South. Không mặc định Role hạn chế hơn luôn thắng.

Kiểm tra: Role Membership, Filter Direction, Broken Relationships, Both Security Filter, kết quả sau Publish, Identity và Permissions.

Cập nhật đối chiếu: có nơi trong Module Assessment gợi ý Viewer không thuộc Role thấy toàn bộ dữ liệu; tài liệu RLS chuyên sâu hiện tại nói Reader không thuộc RLS Role trong Model có RLS thường không nhận dữ liệu hoặc không truy vấn được. Nếu ai đó thấy toàn bộ dữ liệu, điều tra quyền chỉnh sửa/Workspace Role và Role không hạn chế, không quy kết chỉ vì thiếu Membership.

Trusted AI

Copilot/Data Agents phải truy vấn dưới danh tính/Effective Identity phù hợp để RLS/OLS được áp dụng. Nếu App dùng Technical Account/Service Principal, không tự suy ra quyền của người cuối.

Exam: View as trước Publish, Test as role sau Publish, Entra Security Groups cho Membership, Workspace Admin/Member/Contributor bypass Reader RLS semantics, Multiple Roles = Union.

Unit 5 — Exercise: Implement RLS for a semantic model

Unit này dạy gì

Tạo Sample Model, Static RLS, Dynamic RLS, kiểm thử và Publish. Đây là quy trình thực hành độc lập theo mục tiêu Unit; không phải Hosted Lab transcript.

Chuẩn bị

Power BI Desktop Windows, Workspace/License phù hợp nếu Publish. Không cần Capacity trả phí cho bước Desktop local. Sample data tạo bằng DAX, không cần Accounts example.com thực.

Bước 1 — Tạo dữ liệu

DimRegion =
DATATABLE(
    "RegionKey", INTEGER,
    "RegionName", STRING,
    {{1,"North"},{2,"Central"},{3,"South"}}
)
FactSales =
DATATABLE(
    "SalesID", INTEGER,
    "RegionKey", INTEGER,
    "Revenue", INTEGER,
    {
        {101,1,100}, {102,1,200},
        {103,2,150}, {104,2,250},
        {105,3,400}, {106,3,500}
    }
)
UserRegionAccess =
DATATABLE(
    "UserUPN", STRING,
    "RegionKey", INTEGER,
    {
        {"alice@example.com",1},
        {"alice@example.com",2},
        {"bob@example.com",3},
        {"carol@example.com",1}
    }
)

Tạo Active Single Direction Relationship: DimRegion[RegionKey] (1) → FactSales[RegionKey] (*). Để UserRegionAccess độc lập vì RLS sử dụng CONTAINS để tra Mapping.

Total Revenue = SUM(FactSales[Revenue])
Current User = USERPRINCIPALNAME()

Kỳ vọng North = 300, Central = 400, South = 900, Total = 1600.

Bước 2 — Static RLS

Modeling → Manage roles → New → North_Only → DimRegion:

[RegionName] = "North"

View as → North_Only: Table chỉ có North, Total = 300.

Bước 3 — Dynamic RLS

Manage roles → New → Dynamic_Region → DimRegion:

CONTAINS(
    UserRegionAccess,
    UserRegionAccess[UserUPN], USERPRINCIPALNAME(),
    UserRegionAccess[RegionKey], DimRegion[RegionKey]
)

View as → chỉ chọn Dynamic_Region → Other user để thử UPN. Không chọn đồng thời hai Roles khi muốn đo riêng Dynamic Role.

UserExpected RegionsRevenue
alice@example.comNorth, Central700
bob@example.comSouth900
carol@example.comNorth300
david@example.comKhông mappingKhông có dữ liệu

Card SUM có thể hiển thị BLANK với User không có mapping. Kiểm tra cả Current User và nguồn UPN trong Service.

Bước 4 — Publish và Role Membership

Home → Publish → Workspace phù hợp → Semantic Model → Security → Dynamic_Region → thêm User hoặc Entra Security Group hợp lệ. User cần cả quyền truy cập Report/Semantic Model phù hợp. Gán Role không thay thế Report Access.

Bước 5 — End-to-end verification

  • Test Static North = 300.
  • Dynamic Alice = 700, Bob = 900, Carol = 300.
  • User không mapping = không có dữ liệu.
  • Viewer thực được áp dụng RLS, Contributor không phải cơ chế hạn chế dữ liệu như Viewer.
  • Test Multi-role Union và Identity thật khi cần.

Unit 6 — Module assessment

Câu 1 — Managers đổi Region, không muốn sửa Model: A Static RLS per Region; B Dynamic RLS + UPN + Mapping; C OLS. Đáp án B. Mapping cập nhật theo quyền, OLS chỉ bảo vệ Tables/Columns.

Câu 2 — Manager xem EmployeeName nhưng không Salary: A RLS; B OLS Salary; C xóa Salary tạo model riêng. Đáp án B. RLS lọc dòng; OLS bảo vệ Column. Model riêng có thể là phương án kiến trúc nhưng không cần cho yêu cầu này.

Câu 3 — Viewer thấy toàn dữ liệu, đề gợi ý chưa gán RLS Role: A DAX Syntax; B Missing Role Assignment; C DirectQuery. Đáp án Module hướng tới B, nhấn mạnh phải quản lý Membership. Nhưng cần hiệu chỉnh khi áp dụng Production: tài liệu RLS chuyên sâu hiện tại không ủng hộ kết luận một Viewer không có RLS Role sẽ tự thấy toàn dữ liệu; cần kiểm tra các quyền chỉnh sửa, Role không hạn chế và User identity.

Câu 4 — Test RLS trước Publish: A Modeling → View as; B Publish rồi chờ Users; C chỉ xem Formula. Đáp án A. View as kiểm tra Role và Filter Propagation trực tiếp trong Desktop.

Câu 5 — 200 Salespersons thuộc 5 Regions: A add users one-by-one; B Microsoft Entra Security Groups; C Microsoft 365 Groups. Đáp án B. Entra Security Groups phù hợp quản trị Role Membership; Microsoft 365 Groups không được hỗ trợ trực tiếp.

Unit 7 — Summary

RLS lọc dòng; OLS bảo vệ Tables/Columns; Dynamic RLS + UPN + Mapping cho quyền theo User; View as/Test as role và kiểm thử Viewer thật xác nhận Security. Workspace Role và quyền chỉnh sửa quan trọng; khi dùng Copilot/Data Agents phải bảo đảm danh tính được truyền đúng.
