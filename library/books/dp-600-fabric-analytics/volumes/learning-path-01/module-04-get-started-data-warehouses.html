Unit 1 — Introduction

Unit này dạy gì

Vì sao sử dụng Fabric Warehouse cho bài toán phân tích dữ liệu quan hệ, có lịch sử và nhiều phép tổng hợp.

Nội dung chính trong Unit

Nguồn dữ liệu doanh nghiệp nằm trong ERP, CRM, Dataverse, SQL và files. Warehouse chuẩn hóa dữ liệu thành các bảng có cấu trúc để tính doanh thu, tồn kho, hiệu quả theo thời gian, khách hàng hoặc sản phẩm. Fabric Warehouse là hệ thống được quản lý hoàn toàn trong Fabric, không phải tự dựng SQL Server VM, đồng thời lưu dữ liệu dưới nền Delta/OneLake.

Tính năng chính: transactional T-SQL với CREATE TABLE, INSERT, UPDATE, DELETE, MERGE, joins, aggregates, SQL Views, Stored Procedures; kết nối Power BI và các SQL clients. Khác với Lakehouse SQL analytics endpoint, Warehouse cho phép sửa underlying data bằng T-SQL được hỗ trợ.

flowchart TB
  S[ERP / CRM / Dataverse / SQL / Files] --> I[Data Factory / Dataflows / COPY INTO]
  I --> W[Fabric Warehouse]
  W --> T[Staging + Fact/Dimension + Views]
  T --> P[Power BI semantic model]
  T --> AI[AI / Data agents khi hỗ trợ]

Ví dụ: Doanh nghiệp từng có SQL Views trong Synapse Serverless SQL Pool. Khi chuyển sang Fabric phải đánh giá lại engine, khả năng DML, loại tables, SQL syntax và cost; không khẳng định toàn bộ SQL View cũ tương thích 100%.

Unit 2 — Understand data warehouses

Unit này dạy gì

Giới thiệu Data Warehouse và mô hình dữ liệu đa chiều, bao gồm Fact, Dimension, Time Dimension, Slowly Changing Dimensions và Star/Snowflake.

Nội dung chính trong Unit

Operational database vs Data Warehouse

OLTP database ưu tiên giao dịch ngắn, độ chính xác và cập nhật trạng thái. Warehouse ưu tiên báo cáo lịch sử và tính toán tổng hợp trên nhiều nguồn. Một warehouse vẫn cho phép DML; khác biệt nằm ở workload và cách mô hình hóa, không phải cứ Warehouse thì chỉ SELECT.

Quá trình triển khai Warehouse thường có Data ingestion → Storage → Processing → Analysis and delivery.

Design a data warehouse — Tables

Fact table: Lưu các sự kiện có thể định lượng. Ví dụ:

DateKeyProductKeyCustomerKeyQuantitySalesAmount

20261101103211300000

Dimension table: Mô tả ai/cái gì/ở đâu/khi nào. Ví dụ DimProduct(ProductKey, ProductName, Category) cho phép GROUP BY Category khi join FactSales.

Grain: Trước khi thiết kế Fact, phải xác định một dòng đại diện cho cái gì: một order, một order line, hay một daily summary. Nếu grain không rõ, aggregate dễ sai do duplicate joins.

Surrogate Key: Khóa định danh nội bộ Warehouse như ProductKey=101, độc lập với mã từ ERP. Alternate/Business Key: Mã thực thể nguồn như ERP-P0001. Surrogate Keys đặc biệt hữu ích cho SCD Type 2 khi một CustomerID cần nhiều dòng lịch sử.

Special types of dimension tables

Time Dimension / DimDate: Cung cấp DateKey, FullDate, Year, Quarter, Month, Day; tạo hierarchy và so sánh thời gian. Ví dụ:

DateKeyDateYearQuarterMonth
202611012026-11-012026Q411
202611022026-11-022026Q411

Slowly Changing Dimension (SCD):

  • Type 1: Ghi đè giá trị hiện tại, không giữ lịch sử thuộc tính đã đổi. Ví dụ khách hàng sửa lỗi chính tả tên.
  • Type 2: Thêm dòng lịch sử mới, với Surrogate Key mới và thời gian hiệu lực. Ví dụ khách hàng đổi địa chỉ nhưng cần phân tích khu vực tại thời điểm mua hàng.

SCD yêu cầu pipeline giải quyết effective dates, current row và matching giữa Fact với đúng bản Dim có hiệu lực; không chỉ thêm cột ValidFrom là xong.

Data warehouse schema designs

Star schema: Fact ở trung tâm, Dimensions liên kết trực tiếp. Dimension thường denormalize để giảm joins và làm model dễ hiểu. Snowflake schema: Dimension được normalize ra nhiều bảng con, giảm lặp một số thuộc tính nhưng tăng complexity của joins/relationships.

Exam notes: Descriptive attribute → Dimension; Transaction amount/quantity → Fact; Historical attribute changes → SCD; Intuitive analytic model → Star Schema.

Unit 3 — Understand data warehouses in Fabric

Unit này dạy gì

Đặc điểm Fabric Warehouse, tạo bảng, ingest files, sử dụng staging và zero-copy clones.

Nội dung chính trong Unit

Describe a Fabric data warehouse

Fabric Warehouse là fully managed analytical database. Hỗ trợ transactional T-SQL theo tập cú pháp Fabric hỗ trợ, OneLake Delta storage, SQL tooling qua TDS, cross-database query và Copilot khi đủ điều kiện. Không phải toàn bộ SQL Server capabilities đều có thể sử dụng; ví dụ PK/FK constraints trong Fabric Warehouse có giới hạn, nhiều dạng chỉ là NOT ENFORCED.

DDL: CREATE TABLE, ALTER TABLE, DROP TABLE ở phạm vi hỗ trợ. DML: INSERT, UPDATE, DELETE, MERGE với semantics Transaction được hỗ trợ.

Scenario: Read-only T-SQL trên Delta tables → SQL analytics endpoint. Transform/MERGE dimension/fact bằng T-SQL → Warehouse.

Create a data warehouse

Fabric portal → Workspace → New item → Warehouse → đặt tên và tạo. Workspace phải gắn capacity phù hợp. Warehouse có SQL query editor, data explorer và kết nối SQL tooling.

Ví dụ khung COPY INTO (cần cấu hình quyền/credential và URL thật):

COPY INTO dbo.StgSales
FROM 'https://storageaccount.blob.core.windows.net/data/sales.csv'
WITH (FILE_TYPE = 'CSV', FIRSTROW = 2);

OPENROWSET phù hợp với yêu cầu query external files without creating target table first. COPY INTO phù hợp khi muốn nạp file thành dữ liệu vật lý trong bảng Warehouse. Không chọn Pipeline Copy Data khi bài toán chỉ cần truy vấn cross-database trực tiếp.

Cross-database: Cấu trúc SQL ba phần database.schema.table trong phạm vi query engine cho phép:

FROM SalesLakehouse.dbo.FactSales;

Kiểu DECIMAL(p,s) thích hợp cho giá trị tiền cần độ chính xác; FLOAT là xấp xỉ và không nên mặc định dùng cho kế toán. Schema phải phù hợp source data.

Use staging tables for data loading

Staging là khu tiếp nhận dữ liệu nguồn để validate, deduplicate, clean, map business keys thành surrogate keys và nạp bảng Fact/Dimension. Ví dụ:

INSERT INTO dbo.FactSales
    (SalesKey, CustomerKey, ProductKey, DateKey, SalesAmount, Quantity)
SELECT
    s.OrderID,
    c.CustomerKey,
    p.ProductKey,
    d.DateKey,
    s.Amount,
    s.Qty
FROM dbo.StgSales AS s
JOIN dbo.DimCustomer AS c ON s.CustomerID = c.CustomerAltKey
JOIN dbo.DimProduct AS p ON s.ProductID = p.ProductAltKey
JOIN dbo.DimDate AS d ON s.OrderDate = d.DateValue;

Mẫu minh họa giả định các bảng/columns tồn tại. Production cần kiểm tra unmatched dimension keys và duplicate records: INNER JOIN có thể làm mất các dòng chưa match.

Understand table clones

Zero-copy clone tạo một table logic độc lập từ snapshot hiện tại, không sao chép toàn bộ data files ban đầu.

CREATE TABLE dbo.FactSales_Test
AS CLONE OF dbo.FactSales;

Bảng gốc thay đổi sau khi clone không tự đồng bộ sang clone; sửa clone cũng không thay đổi gốc. Thường dùng test changes, migration rehearsal hoặc phục hồi trong giới hạn retention được hỗ trợ. Khác Shortcut: Shortcut tham chiếu dữ liệu nguồn cập nhật; Clone có trạng thái độc lập tại thời điểm tạo. Giới hạn: không giả định clone được giữa mọi Warehouses/Workspaces hoặc chạy trên Lakehouse SQL endpoint.

Exam notes

Write T-SQL → Warehouse; Bulk load → COPY INTO; Read external file → OPENROWSET; Source keys → surrogate keys → Staging; Independent test snapshot without copying full data → Table Clone.

Unit 4 — Query and transform data

Unit này dạy gì

Sử dụng SQL editor, Visual Query Editor và chuẩn hóa truy vấn bằng Views/Stored Procedures.

Nội dung chính trong Unit

Query data with the SQL query editor

Fabric SQL query editor hỗ trợ syntax highlighting, IntelliSense, validation/completion và có thể có Copilot khi đủ điều kiện. Ví dụ tổng hợp doanh thu theo khu vực:

SELECT
    c.Region,
    SUM(f.SalesAmount) AS TotalSales
FROM dbo.FactSales AS f
JOIN dbo.DimCustomer AS c ON f.CustomerKey = c.CustomerKey
GROUP BY c.Region
ORDER BY TotalSales DESC;

Copilot có thể sinh/giải thích/sửa T-SQL từ prompt như monthly sales by region for last 12 months, nhưng vẫn phải kiểm tra relationships, filter và định nghĩa doanh thu.

Query data with the Visual query editor

Visual query editor tạo filter, merge, group, choose columns bằng giao diện. Ví dụ kéo FactSales và DimProduct, merge trên ProductKey, expand ProductName, group theo ProductName. Phù hợp với low-code exploratory analytics; T-SQL thường hiệu quả hơn cho stored logic phức tạp.

Transform data with views and stored procedures

View: Query definition tái sử dụng làm data surface; khi SELECT, engine thực thi query theo cách hỗ trợ. Nó không tạo bảng vật lý mới như CTAS.

CREATE VIEW dbo.vw_SalesByRegion AS
SELECT c.Region, SUM(f.SalesAmount) AS TotalSales
FROM dbo.FactSales AS f
JOIN dbo.DimCustomer AS c ON f.CustomerKey = c.CustomerKey
GROUP BY c.Region;

SELECT * FROM dbo.vw_SalesByRegion;

Stored procedure: Có thể thực thi logic T-SQL lặp lại, gồm các bước chuyển đổi DML theo khả năng Warehouse.

CREATE PROCEDURE dbo.usp_GetSalesByRegion
AS
BEGIN
    SELECT c.Region, SUM(f.SalesAmount) AS TotalSales
    FROM dbo.FactSales f
    JOIN dbo.DimCustomer c ON f.CustomerKey = c.CustomerKey
    GROUP BY c.Region;
END;

EXEC dbo.usp_GetSalesByRegion;

Views có tên, business semantics và cột rõ ràng hỗ trợ BI/AI hiểu dữ liệu, nhưng vẫn phải quản trị metadata và quyền.

Unit 5 — Model data in a warehouse

Unit này dạy gì

Chuẩn bị và chuẩn hóa dữ liệu Warehouse cho semantic model/reporting, gồm visibility, naming, relationships, SQL views, DAX measures và Direct Lake.

Nội dung chính trong Unit

Prepare data for consumption

Một Warehouse có staging, audit, Fact và Dimension tables. Không nên đưa tất cả kỹ thuật columns/tables vào field list của semantic model. Các biện pháp:

  1. Hide internal objects: Ẩn Staging tables, surrogate keys kỹ thuật, ETL flags khỏi field list; ẩn field không phải là data security.
  2. Friendly names: CustRgn → Customer Region, giúp analyst và Copilot hiểu.
  3. Descriptions: Giải thích chính xác Billing Region so với Shipping Region hay Net Revenue có/không gồm thuế.
Understand relationships between tables

Trong Star Schema, Fact thường chứa nhiều dòng tham chiếu một Dimension: FactSales (*) → (1) DimCustomer. Cross-filter single direction từ Dimension sang Fact thường là mặc định dễ quản lý; bi-directional có thể gây ambiguity/performance issues nếu dùng tùy ý.

SQL foreign keys ≠ semantic relationships. Một relationship trong semantic model không tự enforce referential integrity ở Warehouse, và Fabric Warehouse PK/FK có các giới hạn riêng.

Standardize data access with views and measures

View chuẩn hóa SQL JOIN hoặc transformation để nhiều consumers dùng chung; DAX measure chuẩn hóa phép tính phản ứng theo filter context trong semantic model.

Total Sales = SUM(FactSales[SalesAmount])

Ví dụ View chuẩn hóa điều kiện completed sales, còn measure Total Sales tính theo Product, Date, Region mà report đang filter. Không bắt buộc mọi KPI đều là cột vật lý trong Warehouse.

Create a semantic model for Power BI reporting

Semantic model chứa tables, relationships, measures, hierarchies, descriptions và RLS theo phạm vi hỗ trợ. Direct Lake đọc dữ liệu Delta-Parquet từ OneLake theo cơ chế riêng, tránh Import truyền thống. Framing cập nhật metadata về trạng thái bảng Delta; không nên hiểu dữ liệu luôn cập nhật tức thì nếu chưa có framing/refresh phù hợp.

Tính năngDirect Lake on OneLakeDirect Lake on SQL

AI readiness: Friendly names, business definitions và relationships đúng sẽ cải thiện khả năng dùng Copilot/data agents nhưng không tự bảo đảm kết quả đúng.

Exam notes

Fact-Dim → Many-to-one; Standard filtering → Single from Dim to Fact; Reusable SQL query → View; DAX business metric → Measure; Fabric model without Import → Direct Lake.

Unit 6 — Secure and monitor a warehouse

Unit này dạy gì

Phân biệt các lớp quyền truy cập và công cụ theo dõi truy vấn hiện tại/lịch sử.

Nội dung chính trong Unit

Security — Workspace roles

Admin/Member/Contributor/Viewer điều khiển phạm vi quản lý Workspace. Viewer không đồng nghĩa mọi data-level access được cấp; cần cân nhắc item permissions và granular SQL security.

Item permissions
QuyềnÝ nghĩa
ReadKết nối vào SQL endpoint của Warehouse, không đồng nghĩa có quyền SELECT tất cả bảng
ReadDataĐọc các tables/views trong Warehouse theo mô hình hỗ trợ
ReadAllĐọc dữ liệu OneLake/Parquet gốc trong phạm vi quyền

Scenario: Chỉ chia sẻ Warehouse cho downstream consumer mà không cả Workspace → item permissions. Chỉ cần connect → Read; query all SQL tables → ReadData; truy cập raw OneLake data → ReadAll, cần quản lý cẩn thận.

Granular SQL security
  • Object-level security: GRANT/DENY theo table, view, stored procedure.
  • RLS: Giới hạn dòng. Ví dụ Sales South chỉ xem Region='South'.
  • CLS: Giới hạn cột. Ví dụ cấm analyst đọc CustomerEmail.
  • DDM: Dynamic Data Masking che một phần giá trị trong SQL query result cho người không có quyền unmask. DDM không phải encryption và không thay thế cơ chế chặn truy cập file dữ liệu gốc.

SQL endpoint policies không nhất thiết áp dụng qua tất cả OneLake/Spark paths. Nếu người dùng được cấp ReadAll hoặc model dùng Direct Lake on OneLake, phải đánh giá đường truy cập riêng. Đây là một trong các rủi ro security quan trọng nhất khi triển khai.

Monitoring — Query insights

Query insights cho biết lịch sử truy vấn, theo tài liệu module giữ dữ liệu khoảng 30 ngày. Các views đáng nhớ:

ViewMục đích
queryinsights.execrequestshistoryLịch sử SQL requests hoàn tất
queryinsights.longrunningqueriesTruy vấn chạy dài
queryinsights.execsessionshistorySessions hoàn tất

Ví dụ báo cáo Power BI đột nhiên chậm, Query insights giúp xác định truy vấn gần đây có thời gian xử lý tăng.

Monitoring — Dynamic management views

DMVs hỗ trợ quan sát sessions/requests đang hoạt động:

SELECT request_id, session_id, start_time, total_elapsed_time
FROM sys.dm_exec_requests
WHERE status = 'running'
ORDER BY total_elapsed_time DESC;

Có thể cần quyền quản trị thích hợp để xem hoạt động của người khác hoặc KILL session. Trên Fabric, SQL client connection không mặc nhiên có cùng toàn bộ quyền SQL Server sysadmin.

Exam notes: historical slow requests → Query insights; current running requests → DMVs; restrict rows → RLS; restrict columns → CLS; mask displayed values → DDM.

4. Query Fact + DimDate:

SELECT
    d.[Year] AS CalendarYear,
    d.[Month] AS MonthOfYear,
    d.MonthName,
    SUM(f.SalesTotal) AS SalesRevenue
FROM dbo.FactSalesOrder AS f
JOIN dbo.DimDate AS d ON f.SalesOrderDateKey = d.DateKey
GROUP BY d.[Year], d.[Month], d.MonthName
ORDER BY CalendarYear, MonthOfYear;

Kết quả mỗi năm/tháng có tổng doanh thu. Mở rộng join DimCustomer để thêm CountryRegion:

SELECT
    d.[Year] AS CalendarYear,
    d.[Month] AS MonthOfYear,
    d.MonthName,
    c.CountryRegion AS SalesRegion,
    SUM(f.SalesTotal) AS SalesRevenue
FROM dbo.FactSalesOrder AS f
JOIN dbo.DimDate AS d ON f.SalesOrderDateKey = d.DateKey
JOIN dbo.DimCustomer AS c ON f.CustomerKey = c.CustomerKey
GROUP BY d.[Year], d.[Month], d.MonthName, c.CountryRegion
ORDER BY CalendarYear, MonthOfYear, SalesRegion;

5. Create View: Tái sử dụng logic truy vấn thứ hai, không đưa ORDER BY cuối vào View definition:

SELECT * FROM dbo.vSalesByRegion
ORDER BY CalendarYear, MonthOfYear, SalesRegion;
