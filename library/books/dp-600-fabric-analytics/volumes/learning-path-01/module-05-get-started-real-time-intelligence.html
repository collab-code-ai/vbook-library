Unit 1 — Introduction

Unit này dạy gì

Tại sao phân tích theo batch không đáp ứng những quyết định vận hành cần phản ứng ngay khi sự kiện phát sinh.

Nội dung chính trong Unit

Một công ty vận chuyển có GPS, scans kiện hàng, trạng thái giao hàng và phản hồi khách hàng. Nếu pipeline chỉ chạy cuối ngày, một xe gặp sự cố lúc 9:00 có thể không được báo cáo tới quản lý cho tới ngày hôm sau. Dữ liệu lịch sử có thể đúng nhưng ra quyết định đã muộn.

Batch Analytics: gom và xử lý dữ liệu theo đợt. Phù hợp báo cáo định kỳ, không cần phản ứng tức thì. Real-Time Analytics: nhận và xử lý dữ liệu liên tục để phát hiện tình trạng đang diễn ra; phù hợp với logistics, monitoring, fraud và operational control.

flowchart TB
  A[Event xảy ra] --> B[Eventstream ingestion]
  B --> C[Store / Analyze]
  C --> D[Dashboard]
  C --> E[Automated alert/action]

Real-time không có nghĩa độ trễ bằng 0; độ trễ tồn tại ở network, ingest, processing, query, trigger và delivery. Các hệ thống gọi là near real-time khi có thời gian xử lý thấp nhưng không tức thì tuyệt đối.

Unit 2 — What is real-time data analytics?

Unit này dạy gì

Phân biệt Event và Stream; hiểu năm thành phần của giải pháp real-time và giá trị nghiệp vụ.

Nội dung chính trong Unit

Understand events and streams

Event là một bản ghi mô tả sự kiện tại một thời điểm. Ví dụ:

{
  "machineId": "M001",
  "timestamp": "2026-11-15T09:00:00Z",
  "temperature": 85.5,
  "status": "Warning"
}

Các hệ thống khác có Event như khách thêm sản phẩm vào giỏ, app phát lỗi, giao dịch thanh toán, xe thay đổi GPS, hàng được scan ở kho. Event không nhất thiết là error.

Stream là luồng nhiều Events liên tục: cảm biến M001 phát nhiệt độ 76.2°C lúc 09:00:00, 79.4°C lúc 09:00:05, 83.1°C lúc 09:00:10, 91.5°C lúc 09:00:15. Hệ thống streaming có thể phát hiện ngưỡng 90°C ngay khi thấy giá trị tương ứng.

Lưu ý Event time (lúc sự kiện xảy ra) có thể khác Ingestion/Processing time (lúc dịch vụ nhận/xử lý). Sự kiện đôi khi đến trễ hoặc sai thứ tự, nên production analytics cần chọn cách xử lý timestamp phù hợp.

Components of real-time analytics solutions — 5 thành phần
Thành phầnTrách nhiệmVí dụ
Real-time ingestionNhận dữ liệu liên tụcAzure Event Hubs / Kafka / IoT Hub

Low-latency storageLưu để query events nhanhEventhouse / KQL database

Ví dụ: Filter Events Temperature>80, nhóm theo MachineId và tính trung bình trong rolling window, ghi KQL table, hiển thị dashboard và cảnh báo nếu vượt ngưỡng. Tạo dashboard không đồng nghĩa tự động trigger Alert.

Use real-time analytics — 4 lợi ích
  1. Respond immediately: Hành động nhanh trước vấn đề/giao dịch bất thường.
  2. Optimize operations: Cân đối nhân lực, điều phối vận tải, tối ưu tài nguyên.
  3. Enhance customer experiences: Thông báo tình trạng đơn hàng và thay đổi kịp thời.
  4. Prevent issues: Cảnh báo sớm thiết bị có nguy cơ hư hỏng hoặc hệ thống đang suy giảm.

Exam note: Event là record; Stream là chuỗi records. Real-time analytics bao gồm ingest + process + store + visualize + act, không chỉ Dashboard.

Real-Time Intelligence components

Eventstream: Ingest, filter, transform và route dữ liệu đang chuyển động. Ví dụ Event Hubs → Eventstream → Eventhouse. Eventstream không phải kho lưu lịch sử chính.

Eventhouse: Môi trường lưu/truy vấn event, log và time-series; có thể có nhiều KQL databases và tables như MachineTemperature, MachineErrors, ProductionStatus.

KQL Queryset: Nơi viết, lưu và chia sẻ truy vấn Kusto Query Language.

Real-Time Dashboard: Các Tiles từ KQL queries, có thể tự làm mới và filter tương tác.

Activator: Đánh giá Events hoặc KQL query results theo Rules, gửi email, kích hoạt Power Automate, Pipelines/Notebooks khi được hỗ trợ. Nó không bắt buộc đọc nguồn từ Dashboard.

Real-Time hub: Điểm khám phá các streaming sources và KQL tables mà người dùng có quyền; không phải Eventhouse. Các nhóm nguồn được nêu gồm Data sources, Azure sources, Fabric events và Azure events.

Ví dụ nhà máy 500 thiết bị: mỗi thiết bị gửi Events 10 giây/lần → Eventstream ingest → Eventhouse lưu trữ → KQL tính trung bình/nhiệt độ cao → Dashboard hiển thị → Activator gửi thông báo quá ngưỡng. Nếu cần batch historical analysis và doanh thu, có thể route thêm dữ liệu vào Lakehouse; không phải mọi giải pháp bắt buộc route nhiều đích.

Unit 4 — Ingest and transform real-time data

Unit này dạy gì

Sử dụng Eventstreams và Direct Ingestion; phân biệt eventstream transformations với KQL update policies.

Nội dung chính trong Unit

Eventstreams for data ingestion and transformation

Mô hình Source → Optional Transformation → Destination. Ví dụ sensor gửi {sensorId, temperature, factory, timestamp}; chỉ lọc Temperature>80 rồi route vào một destination. Nếu cần lưu raw dữ liệu để kiểm toán, có thể route raw đến đích riêng thay vì loại bỏ ngay từ source.

Data sources
Nhóm nguồnVí dụ
Microsoft streaming servicesAzure Event Hubs, Azure IoT Hub, Azure Service Bus
Database change eventsCDC từ source database được hỗ trợ
Azure eventsBlob Storage events
Fabric eventsOneLake, item/job events được hỗ trợ
ExternalApache Kafka, Google Cloud Pub/Sub, MQTT trong trạng thái hỗ trợ tương ứng

CDC (Change Data Capture) ghi nhận inserts/updates/deletes hoặc thay đổi dữ liệu trong nguồn, khác với một full refresh batch định kỳ. Không phải mọi nguồn CDC đều hỗ trợ cùng cơ chế và quyền.

Event transformations — các nhóm chức năng chính thức
  1. SQL code: SQL transformations được Eventstream hỗ trợ, không phải một stored procedure T-SQL Warehouse.
  2. Filter: Giữ những Events thỏa điều kiện, như Temp>80.
  3. Manage fields: Chọn/bỏ/đổi tên fields, ví dụ temp → Temperature.
  4. Aggregate: SUM, COUNT, AVG trong windows/logic hỗ trợ.
  5. Group by: Tổng hợp theo MachineId/Region.
  6. Expand: Mở rộng nested structures, đặc biệt JSON payload.
  7. Join: Kết hợp streams/reference data phù hợp với các operator hỗ trợ.

Time windows bổ trợ quan trọng: Tumbling windows không chồng lấp, Hopping windows có thể chồng lấp, Sliding windows theo dòng thời gian/sự kiện. Ví dụ tính AVG(Temp) theo mỗi cửa sổ 5 phút; nếu tính trung bình toàn lịch sử sẽ không phản ánh trạng thái gần đây. Chỉ coi đây là kiến thức giải thích thêm, không phải heading riêng của Unit.

Data destinations
DestinationVai trò
KQL database/EventhouseLưu để phân tích KQL
LakehouseLưu dữ liệu phục vụ BI/data engineering
Derived streamTạo luồng được xử lý cho consumer khác

Eventstream có thể route đến nhiều destination, theo khả năng hỗ trợ của item và cách cấu hình.

Direct ingestion to a KQL database

Không phải mọi nguồn đều cần Eventstream. Eventhouse → KQL database → Get data có thể ingest từ local file, Azure Storage, S3, Event Hubs, OneLake và nguồn hỗ trợ khác. Nếu có sẵn một file logs muốn query KQL, direct ingestion có thể đơn giản hơn tạo Eventstream riêng.

Data transformation with update policies

Update Policy chạy logic KQL đã cấu hình khi source KQL table nhận dữ liệu mới, có thể ghi bảng processed riêng:

Eventstream → RawMachineEvents → Update Policy → ProcessedMachineEvents

Eventstream transformation chạy trước destination, phù hợp lọc/route on-the-fly. Update Policy chạy trong KQL database theo ingestion của bảng nguồn. Ví dụ giữ raw events nhưng tự tạo parsed/validated KQL table là use case của Update Policy.

Exam notes

Before destination → Eventstream Transformation; After ingestion to KQL table → Update Policy; Read raw file into KQL → Direct Ingestion; Store real-time events → Eventhouse.

Unit 5 — Store and query real-time data

Unit này dạy gì

Sử dụng Eventhouse/KQL databases và query bằng Kusto Query Language; hiểu management commands, Materialized Views, Stored Functions, SQL subset và Copilot.

Nội dung chính trong Unit

Eventhouse và KQL database

Eventhouse tổ chức KQL databases. KQL database chứa KQL tables, stored functions, materialized views, shortcuts và các đối tượng hỗ trợ. KQL Queryset là nơi chạy/saved query chứ không phải một bảng dữ liệu.

Understand the power of KQL

Kusto Query Language (KQL) chuyên phục vụ event/time-series/log analytics. Có mặt trong Azure Data Explorer, Azure Monitor Log Analytics, Microsoft Sentinel và Fabric Eventhouse. Phù hợp truy vấn cắt theo thời gian, filter và aggregate khối lượng events lớn.

Get familiar with KQL syntax

KQL sử dụng pipeline operators nối bằng dấu |. Đọc từ bảng, đưa tập kết quả qua từng bước:

stock
| take 10

take 10 không mặc định là 10 records mới nhất. Nếu muốn thứ tự, phải sort/order by trường thời gian.

Where:

MachineEvents
| where Temperature > 80

Project:

MachineEvents
| project MachineId, Timestamp, Temperature

Summarize:

MachineEvents
| summarize AvgTemp = avg(Temperature) by MachineId

Ago(time filter):

MachineEvents
| where Timestamp > ago(1h)

Kết hợp:

MachineEvents
| where Timestamp > ago(1h)
| where Temperature > 80
| summarize
    AvgTemp = avg(Temperature),
    MaxTemp = max(Temperature),
    EventCount = count()
    by MachineId
| order by AvgTemp desc

Bẫy: Kết quả AvgTemp chỉ tính từ sự kiện vượt 80, không phải trung bình toàn bộ nhiệt độ một giờ gần nhất. Filter trước aggregate làm thay đổi ý nghĩa nghiệp vụ.

Query cổ phiếu từ lab/Microsoft Learn:

stock
| where todatetime(["time"]) > ago(5m)
| summarize avgPrice = avg(todouble(bidPrice)) by symbol
| project symbol, avgPrice

todatetime chuyển thời gian; ago(5m) là 5 phút; todouble/todecimal chuyển numeric; summarize by symbol nhóm theo mã cổ phiếu; project chọn columns.

Ví dụ 2 events ABC có bidPrice 100 và 110, AVG =105; XYZ có 200 và 220, AVG =210 nếu đều trong filter 5 phút.

Automate data processing with management commands

Update Policies: Transform khi KQL table nhận dữ liệu, thường từ raw → processed table.

Materialized Views: Lưu kết quả tổng hợp được materialize/duy trì; hữu ích cho những truy vấn lặp đi lặp lại trên dữ liệu lớn. Khác View thông thường chỉ lưu query definition. Cần hiểu tradeoff compute/storage và phạm vi query hỗ trợ.

Stored Functions: Lưu logic KQL có thể tái sử dụng trong queries. Khác Stored Procedure T-SQL dùng trong Warehouse.

Other query options — Using SQL

KQL database hỗ trợ một subset của T-SQL:

SELECT TOP 10 * FROM stock;

Nhưng Eventhouse không vì thế mà trở thành Fabric Warehouse hỗ trợ toàn bộ transactional DML/DDL. KQL vẫn là ngôn ngữ chính để phân tích events/time series.

Use Copilot

Copilot for Real-Time Intelligence có thể hỗ trợ sinh/gợi ý KQL từ ngôn ngữ tự nhiên trong môi trường đủ điều kiện. Ví dụ show top 10 machines with highest average temperature in last hour. Kiểm tra bảng, timestamp, filter, aggregate và business meaning trước khi sử dụng query. Licensing/capacity/permissions có thể giới hạn Copilot.

Exam notes

Time-series query language → KQL; Saved queries → KQL Queryset; Precomputed aggregation → Materialized View; Reusable KQL logic → Stored Function; Transform ingested records → Update Policy.

Unit 6 — Visualize real-time data

Unit này dạy gì

Tạo Real-Time Dashboard và phân biệt với Power BI.

Nội dung chính trong Unit

Create a Real-Time Dashboard

Dashboard chứa nhiều Tiles, mỗi Tile dùng KQL query. Ví dụ: Active Machines, Avg Temperature, Critical Alerts và Temperature Trend. Có thể tạo từ KQL Queryset bằng Save to dashboard hoặc tạo Dashboard trong workspace.

Ví dụ một Tile:

MachineEvents
| where Timestamp > ago(30m)
| summarize ErrorCount = count() by MachineId
| order by ErrorCount desc

Có thể đổi loại visual từ Table sang Column/Line chart, filter theo Region/Plant hoặc cấu hình Live refresh. Tần suất Dashboard refresh (ví dụ 10 giây) không phải SLA ingest 10 giây; query refresh và việc nhận events là hai cơ chế riêng, đều có thể tiêu thụ compute.

Visualize real-time data with Power BI

Power BI phù hợp khi cần semantic model, DAX, relationships, drilldown và dimensional analytics kết hợp nhiều nguồn. Real-Time Dashboard phù hợp operational monitoring dựa KQL query/Tiles. Hai công cụ có thể kết hợp cùng giải pháp.

Use cases for Activator

Các tình huống được bài học giới thiệu: inventory, customer engagement, resource allocation, marketing actions, perishable-goods temperature, app experience, orders không cập nhật, tài khoản vượt ngưỡng, pipeline failures.

Ví dụ order không cập nhật: OrderId SO1001, Status InTransit, LastUpdated 08:00. Nếu đến 10:00 không có sự kiện mới, Rule có thể phát cảnh báo theo logic time-based condition. Đây là kiểm tra sự vắng mặt của update, khác với điều kiện một số đo vượt threshold.

Nguồn Rule: Có thể theo stream events hoặc chạy query-based monitoring theo lịch trên dữ liệu KQL/Realtime Dashboard được hỗ trợ. Query mỗi 5 phút không đồng nghĩa sự kiện được đánh giá ngay khi đến.

Actions: Email, Power Automate, Fabric Pipeline/Notebook và các action được hỗ trợ. Với production phải xét throttling, trigger duplicates, quyền kết nối, idempotency, logging và xử lý lỗi.

Tên cũ/tên mới: Data Activator là cách gọi trước đây; giáo trình hiện dùng Activator.

Exam notes

Business entity → Object; Measurement → Property; Condition for action → Rule; Send alert or trigger workflow → Activator. Dashboard chỉ quan sát; Activator mới có Rule/Action.
