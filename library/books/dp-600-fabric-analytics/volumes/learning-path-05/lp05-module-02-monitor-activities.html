Unit 1 — Introduction

Unit này dạy gì

Hiểu tại sao cần giám sát trạng thái và chất lượng vận hành của toàn bộ quá trình xử lý dữ liệu, không chỉ một job riêng lẻ.

Nội dung chính trong unit

Ví dụ dòng dữ liệu:

flowchart TD
 D[Dataflow Gen2: nạp dữ liệu] --> L[Lakehouse: lưu dữ liệu]
 L --> N[Spark Notebook: biến đổi]
 N --> S[Semantic Model]
 S --> R[Power BI Report]

Dataflow hằng ngày có thể thất bại do nguồn đổi schema. Notebook vẫn chạy thành công trên dữ liệu cũ; report vẫn mở bình thường. Vì thế, người dùng có thể xem data stale mà không biết. Monitoring phải xét trạng thái, thời gian, xu hướng, retry, dependencies, freshness và đôi khi dữ liệu đầu ra.

Ba khả năng được giảng:

  • Monitoring hub: Theo dõi job runs gần đây, trạng thái và chi tiết.
  • Workspace monitoring: Diagnostic logs/metrics sâu hơn, truy vấn bằng KQL.
  • Activator: Phản ứng tự động với Fabric events bằng notifications hoặc khởi chạy hoạt động khác.

Monitoring phát hiện/chẩn đoán vấn đề, còn Activator hỗ trợ phản ứng; không tự bảo đảm mọi sự cố được khắc phục.

Unit 2 — Understand monitoring

Unit này dạy gì

Hiểu monitoring, năm loại Fabric activities và phương pháp xây dựng baseline để nhận diện bất thường.

2.1. Why monitoring matters

Monitoring là thu thập, quan sát và phân tích hoạt động nhằm xác định tình trạng hệ thống và sự suy giảm hiệu năng.

NhómCâu hỏi
Execution statusJob thành công/thất bại/đang chạy?
PerformanceThời lượng và hiệu năng có bất thường không?
ReliabilityLỗi hoặc retries có tăng không?

Ví dụ Notebook chạy thành công trong 25 phút nhưng trước đó thường chỉ 3 phút. Không được bỏ qua chỉ vì status Succeeded: có thể do dữ liệu tăng, data skew, transformation chưa tối ưu, capacity bị cạnh tranh hoặc nguồn chậm.

Một Semantic Model refresh thường xuyên retry rồi mới thành công cũng có thể báo hiệu hệ thống nguồn không ổn định.

2.2. Types of Fabric activities to monitor

A. Data pipelines

Data Pipeline điều phối nhiều activities như:

Copy Data → Run Notebook → Execute SQL → Refresh Semantic Model

Cần theo dõi pipeline run status, activity run status, start/end times, duration, error details.

Ví dụ:

ActivityKết quả
Copy DataSucceeded
Validate Row CountFailed
Send WarningSucceeded

Một pipeline có failure-handling logic có thể hoàn tất theo trạng thái cuối cho phép, dù activity ở giữa thất bại. Đừng mặc định mọi activity thành công chỉ từ trạng thái pipeline. Để điều tra, mở activity run cụ thể.

B. Dataflow Gen2

Dataflow Gen2 ingest/transform qua Power Query. Có thể chạy manual, scheduled, từ Data Pipeline. Theo dõi start/end, duration, status, error details.

Ví dụ file nguồn thay đổi kiểu dữ liệu cột OrderDate → Power Query conversion error. Từ Monitoring hub, mở Dataflow run và tìm query/table bị lỗi. Không mặc định mọi query hay destination đều bị lỗi nếu chỉ một bước thất bại.

C. Semantic model refreshes

Theo dõi refresh result, duration, retries, reliability và lịch sử. Ví dụ:

NgàyRetryStatus
Thứ Hai0Succeeded
Thứ Ba1Succeeded
Thứ Tư2Succeeded
Thứ Năm3Succeeded

Retry tăng liên tục là dấu hiệu cần điều tra dù cuối cùng refresh đều thành công. Import, Direct Lake và DirectQuery có cơ chế dữ liệu khác nhau; không mặc định mọi Semantic Model đều dùng full Import refresh.

D. Spark jobs and notebooks

Theo dõi job progress, execution duration, Spark logs, resource usage và lỗi. Ví dụ phép join tăng từ 1 triệu lên 40 triệu dòng có thể gặp data skew hoặc shuffle tốn tài nguyên. Dùng Monitoring hub để xác định job, sau đó Spark monitoring/logs để tìm bottleneck.

E. Eventstreams

Eventstream xử lý liên tục, khác batch job có điểm bắt đầu/kết thúc rõ. Theo dõi:

MetricDiễn giải
Ingestion throughputLượng dữ liệu ingest trên một khoảng thời gian
LatencyĐộ trễ chuyển tiếp/xử lý
Error rateTỷ lệ ingest/processing errors

Ví dụ thiết bị IoT gửi nhiệt độ mỗi giây vào Eventhouse. Throughput đột ngột giảm có thể do upstream ngừng gửi. Latency tăng khiến báo cáo real-time bị chậm.

Scenario: Batch tập trung status/duration; streaming phải thêm throughput/latency/error rate.

2.3. Establish a monitoring baseline

Baseline là tham chiếu cho hành vi thông thường của hệ thống. Ví dụ sáu ngày đầu Dataflow chạy 4–5 phút, ngày thứ bảy chạy 20 phút nhưng vẫn Succeeded. Đây là performance anomaly.

Microsoft Learn hướng dẫn năm hoạt động:

  1. Track metrics consistently: Dùng nhất quán duration, status, error rates, retries qua nhiều lần chạy.
  2. Define normal behavior: Dựa trên historical runs để xác lập dải thường gặp (ví dụ 3–5 phút).
  3. Set up notifications: Gửi cảnh báo khi job thất bại thay vì chờ người trực mở portal.
  4. Investigate anomalies promptly: Điều tra ngay cả khi status Succeeded nhưng duration/retries tăng.
  5. Review and adjust: Baseline thay đổi cùng data volume và workloads; không giữ ngưỡng cứng mãi mãi.

Exam notes

Succeeded but slow, retry patterns, historical trends, unexpected duration → Kiểm tra historical runs và baseline, đừng bỏ qua hay xóa/recreate job khi chưa biết nguyên nhân.

Unit 3 — Use the Microsoft Fabric monitoring hub

Unit này dạy gì

Dùng Monitoring hub để xem trạng thái, chi tiết, lịch sử, filters, notifications; biết khi nào cần Workspace monitoring để phân tích logs bằng KQL.

3.1. Open the monitoring hub

Trong giao diện được module giảng: Microsoft Fabric → Monitor, phần Activities thường có Activity name, Status, Item type, Start time, Duration, Location. Đây là nơi tập trung những runs người dùng có quyền truy cập.

Cập nhật UI 2026: Tài liệu giới thiệu Monitor hub mới với các khu như Job runs, Alerts, Applications, Capacity and cost, Agents. Để xem job runs, vào khu tương ứng. UI và tên nút có thể khác ảnh trong Learn; Monitor hub mới được ghi nhận Preview tại thời điểm bài giảng.

3.2. Understand activity status

StatusÝ nghĩaHành động
SucceededHoàn thànhSo sánh duration nếu bất thường
FailedThất bạiXem errors/logs
In progressĐang chạyKiểm tra progress/duration
CancelledBị dừngTìm nguyên nhân cancel

Giao diện mới còn có thể hiển thị Queued, Not started. Không phải mọi Succeeded đều có dữ liệu đầu ra đúng về nghiệp vụ.

3.3. View activity details

Trong module: Monitor → Activity → View details. Xem Start time, End time, Duration, Status, Error codes/messages, metadata theo item type.

  • Dataflow lỗi schema → xem query/transformation và source fields.
  • Notebook lỗi → mở Spark application/logs.
  • Data Pipeline lỗi → xuống activity cụ thể, không chỉ xem pipeline status.

Monitor hub mới có thể cung cấp Run history, Advanced details, activity table hoặc Gantt chart tùy loại job.

3.4. View historical runs

Monitor → [Item] → ... → Historical runs trong UI được module mô tả. Lịch sử có thể xem trong khoảng tối đa 30 ngày theo giao diện và retention được hỗ trợ; ở UI mới tìm Run history.

NgàyDurationStatus
10/115 phútSucceeded
11/115 phútSucceeded
12/118 phútSucceeded
13/1112 phútSucceeded
14/1118 phútFailed

Bảng cho thấy suy giảm từ trước khi failure xuất hiện. Historical runs trả lời: lỗi bắt đầu lúc nào, job có chậm dần không, retry có lặp lại không?

3.5. Filter and customize the view

Đối với hàng trăm jobs, lọc theo Status, Item type; chọn columns như Activity name, Location, Duration, End time, Submitted by, Refresh type.

Ví dụ: Monitor → Filter → Status: Failed → Item type: Dataflow Gen2 để chỉ xem failed Dataflow jobs. UI mới có Manage view → Column options và Saved views theo tính năng hỗ trợ.

3.6. Manage failure notifications

Schedule failures phục vụ email khi scheduled job thất bại. Trên Monitor hub mới, tài liệu mô tả đường dẫn kiểu:

Monitor → Manage → Alerts → Schedule failure emails → Configure notifications

Chọn item và recipients. Ví dụ DailySalesLoad chạy 02:00, failed → gửi email cho nhóm vận hành.

Giới hạn cần nhớ:

  • Thường yêu cầu Workspace Contributor hoặc Write permission trên item để cấu hình.
  • Áp dụng cho scheduled runs, không phải mọi manual runs.
  • Recipients là user/group được hỗ trợ trong Microsoft Entra tenant, gồm B2B guests phù hợp.
  • Semantic Models chưa được hỗ trợ trên Schedule failures page theo tài liệu giảng.
  • Schedule failure email được mô tả miễn phí, còn Activator-based alerts có capacity consumption/chi phí riêng.
  • Một số job alert management features còn Preview.

3.7. Workspace monitoring

Workspace monitoring cho phép thu thập telemetry/diagnostic logs/metrics từ những Fabric items được hỗ trợ vào monitoring database dựa trên Eventhouse/KQL Database, để truy vấn bằng Kusto Query Language (KQL).

flowchart TD
 A[Fabric items: Pipelines / Dataflows / Semantic Models] --> M[Monitoring Item / Eventhouse]
 M --> K[KQL Database: telemetry / logs]
 K --> Q[KQL queries]
 K --> D[Dashboards]
 K --> E[Alerts]

Ví dụ câu hỏi: trong 30 ngày gần nhất, pipeline nào thất bại nhiều nhất? Duration có tăng từng tuần? Nhiều jobs cùng failed có trùng thời điểm throttling hay không?

Ví dụ KQL:

ItemJobEventLogs
| top 100 by Timestamp desc

Lệnh lấy 100 job event records mới nhất theo Timestamp nếu bảng/columns được cung cấp trong cấu hình. Logs/telemetry hỗ trợ phụ thuộc item và workspace.

Cập nhật kiến trúc: Microsoft phát triển cách quản lý bằng Monitoring Item, thay cho chỉ một monitoring Eventhouse legacy. Một Monitoring Item có thể giám sát nhiều workspaces trong các điều kiện thích hợp, với yêu cầu region, capacity và permissions.

Các bước minh họa:

  1. Workspace settings → Monitoring.
  2. Chọn Monitoring Item/Eventhouse đích hoặc tạo mới.
  3. Bật data collection.
  4. Sử dụng KQL để truy vấn.

Lưu ý: Không backfill logs trước khi bật collection; retention mặc định 30 ngày nhưng có thể cấu hình; monitoring database read-only; tiêu thụ Fabric capacity; cần Workspace Admin/tenant settings; logs có thể chứa dữ liệu nhạy cảm nên phải bảo mật.

Unit 4 — Respond to Fabric events with Activator

Unit này dạy gì

Sử dụng Activator để xử lý Fabric job events và tự động gửi notifications hoặc kích hoạt remediation activities.

4.1. Fabric job events

Các sự kiện chính trong module:

EventNghĩa
Job createdJob được tạo/kích hoạt
Job failedJob thất bại
Job succeededJob thành công
Job status changedTrạng thái job thay đổi
flowchart LR
 J[Fabric job] --> E[Fabric job event]
 E --> R[Real-Time hub]
 R --> A[Activator rule]
 A --> X[Email / Teams / Fabric activity]

Phân biệt Event (đã xảy ra gì?), Condition (khi nào phản ứng?) và Action (thực hiện gì?). Ví dụ: event ItemJobFailed của pipeline DailySalesLoad → condition khớp item → post vào Teams channel.

4.2. Set up an alert from Real-Time hub

  1. Real-Time → Fabric events → Job events.
  2. Chọn Set alert.
  3. Trong Monitor, Select source events và chọn loại event, workspace, item.
  4. Ví dụ event type Microsoft.Fabric.JobEvents.ItemJobFailed, workspace Sales-Production, item DailySalesLoad.
  5. Đặt điều kiện On each event nếu muốn phản ứng với mỗi failure đã lọc.
  6. Chọn Action, chẳng hạn Teams Channel post hoặc Run Fabric Activities.
  7. Chọn workspace/Activator item để lưu rule; tạo và kiểm tra cấu hình.

Kết quả mong muốn: job phát sinh event khớp điều kiện thì Activator thực hiện action được cấu hình. Cần kiểm tra quyền, region và trạng thái rule.

4.3. Actions available

A. Email: Gửi email cho người phụ trách khi event khớp. Ví dụ báo Semantic Model refresh succeeded.

B. Teams: Gửi tin nhắn tới cá nhân, group chat hoặc channel. Phù hợp khi cả nhóm cùng xử lý sự cố.

C. Run a Fabric activity: Kích hoạt những item types được hỗ trợ như Dataflow, Pipeline, Spark job, Notebook, Function, Copy job. Ví dụ failure tạo các temporary tables → kích hoạt cleanup Notebook để dọn dẹp.

Không tự động retry mọi trường hợp. Nếu lỗi do source xóa một cột hoặc code logic sai, retry liên tục không xử lý nguyên nhân và có thể gây tác hại. Các actions mở rộng như custom Power Automate/publish business event có thể nằm trong tài liệu ngoài module hoặc Preview.

4.4. When to use Activator vs. Schedule failures

ScenarioChọn
Email khi scheduled Pipeline failedSchedule failure emails
Teams message khi Notebook failedActivator
Notification khi job succeededActivator
Cleanup Notebook sau pipeline failedActivator
Quản lý người nhận email lỗi scheduled jobSchedule failures
Kích hoạt pipeline khác theo eventActivator

Governance/cost: Schedule failure emails được mô tả miễn phí; Activator dùng capacity và có thể phát sinh chi phí. Cần permissions tạo Activator, quyền event source, phù hợp region, network settings. Một số tính năng alerting còn Preview. Không tự động chạy hoạt động tác động lớn lên Production mà không kiểm soát idempotency/quyền/lỗi.

Exam notes

  • See what failed → Monitoring hub.
  • Send simple scheduled failure email → Schedule failures.
  • Respond to job event with Teams/email → Activator.
  • Automatically run cleanup or recovery Notebook → Activator + Run a Fabric activity.
  • Analyze telemetry at scale → Workspace monitoring + KQL.

5.1. Create a workspace

Workspaces → New workspace; tên ví dụ DP600-Monitoring-Lab; chọn capacity hợp lệ; Apply/Create. Kết quả: workspace rỗng có thể tạo Fabric items. Nếu không chọn được capacity, kiểm tra subscription/quyền, không tự kích hoạt paid capacity.

5.2. Create a lakehouse

New item → Lakehouse → Create; tên ProductsLakehouse; bật Lakehouse schemas. Kết quả: có khu Tables và Files, chưa có dữ liệu.

5.3. Create and monitor a Dataflow

  1. Từ Lakehouse chọn Get data → New Dataflow Gen2.
  2. Đặt tên Get Product Data.
  3. Trong Dataflow designer chọn Import from Text/CSV file.
  4. Nhập https://raw.githubusercontent.com/MicrosoftLearning/dp-data/main/products.csv và chọn Anonymous.
  5. Kiểm tra preview; xác nhận destination Lakehouse ProductsLakehouse, bảng products nếu UI yêu cầu.
  6. Chọn Save and run.
  7. Mở Monitor → Activities (hoặc Monitor mới Job runs). Tìm Get Product Data, xem In progress/Succeeded hoặc Failed.
  8. Quay về Lakehouse, Refresh Tables nếu cần, kiểm tra bảng products có dữ liệu.

Kết quả đúng: Dataflow run thành công và bảng products tồn tại, có dữ liệu. Nếu success nhưng không thấy bảng, kiểm tra destination và metadata refresh.

5.4. Create and monitor a Spark notebook

  1. New item → Notebook; đặt tên Query Products.
  2. Notebook Explorer → Add data items → From OneLake catalog.
  3. Thêm ProductsLakehouse và mở phần Tables.
  4. Tại products, chọn ... → Load data → Spark để sinh code cell truy vấn Spark.
  5. Chọn Run all; kiểm tra output.
  6. Stop session khi không còn cần Spark session.
  7. Vào Monitor tìm run của Query Products.

Kết quả đúng: Notebook query được bảng và có thông tin thực thi; có thể xem status, duration và logs/metadata tương ứng.

5.5. Monitor history for an item

  1. Ở Dataflow Get Product Data, chọn Refresh now để tạo lần chạy thứ hai.
  2. Mở Monitor; chọn Dataflow → ... → Historical runs hoặc Run history trên UI mới.
  3. Chọn từng run và View detail.
  4. So sánh Status, Start time, End time, Duration.

Kết quả: phân biệt được ít nhất hai lần chạy của cùng item.

5.6. Customize monitoring hub views

Lọc Status = Succeeded, Item type = Dataflow Gen2 (CI/CD) theo Lab; một số tenant hiện thị tên Dataflow Gen2 nên chọn đúng item type thực tế.

Dùng Column options để xem:

5.7. Clean up resources

Workspace → Workspace settings → General → Remove this workspace; chỉ xóa workspace Lab riêng và đã sao lưu dữ liệu cần giữ.

Năm điểm luyện tay

  1. Tạo và chạy Fabric jobs để sinh runs.
  2. Xem status trong Monitor.
  3. Xem run history theo cùng item.
  4. Sử dụng filters, columns.
  5. Kiểm tra dữ liệu đầu ra, không chỉ status thành công.

  • C. Mặc định tự động gửi alerts khi mọi Data Pipeline failed.

Đáp án B. A thuộc công cụ phát triển/orchestration; C không phải hành vi mặc định của Monitoring hub. Monitoring hub cung cấp tập trung thông tin job run. Mẹo: centralized activity status/history → Monitoring hub. Liên hệ Unit 3.

Câu 2 — Dataflow thường chạy 4 phút, hôm nay 20 phút nhưng Succeeded?

  • A. Bỏ qua vì success.
  • B. Xem activity details và historical runs, đối chiếu baseline.
  • C. Xóa Dataflow và tạo lại ngay.

Đáp án B. A bỏ qua performance degradation; C gây rủi ro, chưa chẩn đoán. Mẹo: Succeeded but unusually slow → baseline + history. Liên hệ Unit 2–3.

Câu 3 — Tự động khắc phục sau job failure bằng hoạt động Fabric?

  • A. Send an email.
  • B. Post a Teams message.
  • C. Run a Fabric activity.

Đáp án C. Email và Teams chỉ thông báo; Run Fabric activity có thể kích hoạt cleanup Notebook/Pipeline theo thiết kế. Mẹo: automate remediation → Activator. Liên hệ Unit 4.

Unit 7 — Summary

Unit này dạy gì

Tổng kết quan sát, phân tích và phản ứng tự động trong Microsoft Fabric.

Nội dung chính trong unit

Lớp 1: Monitoring hub — job runs, status, duration, details, history. Lớp 2: Workspace monitoring — telemetry, KQL logs, trends và dashboards. Lớp 3: Activator — xử lý events bằng Teams/email hoặc chạy Fabric activities.

Ví dụ vận hành: Pipeline failed → Activator gửi Teams → kỹ sư xem Monitoring hub → mở KQL logs khi cần → sửa lỗi/kiểm tra dữ liệu → chạy lại job. Monitoring phát hiện vấn đề, nhưng không tự xác nhận đầu ra nghiệp vụ đã đúng.
