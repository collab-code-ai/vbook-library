Unit 1 — Introduction

Unit này dạy gì

Giới thiệu quản lý vòng đời Fabric items khi nhiều kỹ sư cùng xây dựng giải pháp phân tích dữ liệu.

Nội dung chính trong unit

Ví dụ một doanh nghiệp xây dựng hệ thống gồm Lakehouse, Notebook, Data Pipeline, Semantic Model và Power BI Report. Một kỹ sư chỉnh Notebook, một người sửa Pipeline, người khác chỉnh Semantic Model. Nếu mọi người thay đổi trực tiếp trong Production workspace, nguy cơ là:

  1. Nội dung chưa kiểm thử làm gián đoạn báo cáo.
  2. Những chỉnh sửa cùng đối tượng xung đột hoặc ghi đè.
  3. Không biết ai đổi nội dung nào, vào thời điểm nào.
  4. Khó quay về phiên bản ổn định khi lỗi.
  5. Phát hành Production phụ thuộc vào thao tác thủ công.

Lifecycle management kiểm soát vòng đời item: tạo → sửa → kiểm thử → triển khai → bảo trì. Microsoft Fabric có hai cơ chế quan trọng:

  • Git integration: Quản lý version, branches, commits và hỗ trợ cộng tác.
  • Deployment pipelines: Chuyển các định nghĩa item được hỗ trợ qua những stage/môi trường.

Fabric REST APIs bổ sung tự động hóa. Bạn quản lý không chỉ source code thông thường mà cả những định nghĩa Fabric items hỗ trợ lưu trong Git. Git không thay thế quá trình triển khai, còn deployment không thay thế version control.

Unit 2 — Understand Continuous Integration and Continuous Delivery (CI/CD)

Unit này dạy gì

Phân biệt Continuous Integration, Continuous Delivery và Continuous Deployment; biết vai trò các công cụ của Fabric trong vòng đời phát hành.

2.1. Continuous integration (CI)

Continuous Integration là tích hợp thường xuyên những thay đổi nhỏ từ nhiều developer vào nhánh mã nguồn chung. Khi Developer A sửa Notebook để làm sạch dữ liệu, Developer B sửa phần liên quan của cùng hệ thống, họ không nên phát triển độc lập quá lâu rồi mới tích hợp một lần.

Quy trình thường gặp:

  1. Mỗi developer tạo feature branch riêng.
  2. Thực hiện thay đổi và commit.
  3. Tạo Pull Request.
  4. Chạy các kiểm tra đã được cấu hình (build/validation/tests).
  5. Review, chấp thuận và merge vào nhánh chung.
flowchart TD
 A[Developer A] --> G[Shared Git branch]
 B[Developer B] --> G
 C[Developer C] --> G
 G --> T[Build / Validate / Test]
 T --> R[Phát hiện lỗi tích hợp sớm]

Lưu ý: Chỉ kết nối Git integration trong Fabric không có nghĩa là tất cả unit tests tự động chạy. Bạn phải thiết kế CI workflow phù hợp nếu cần validation, schema tests, data-quality tests hoặc integration tests.

2.2. Continuous delivery

Continuous Delivery đưa thay đổi vào trạng thái sẵn sàng phát hành, có thể còn bước phê duyệt trước khi lên Production.

Code change → Integration → Validation → Test/Staging → Approval → Production

Ví dụ, Semantic Model cập nhật các measure DAX; Test workspace đã được kiểm thử và nhóm vận hành chỉ còn đợi release approval. Đây là Continuous Delivery.

2.3. Continuous deployment

Continuous Deployment tự động triển khai vào Production nếu toàn bộ điều kiện kiểm thử, phê duyệt bằng policy và kiểm soát được cấu hình đều đạt; không cần phê duyệt thủ công cho từng đợt release.

Ví dụ, merge Pull Request → chạy tests → cập nhật Test → validation → tự động đưa sang Production. Cơ chế này phải được cấu hình, không có sẵn chỉ bằng việc tạo Deployment pipeline.

Khái niệmMục tiêuĐiểm phân biệt
Continuous IntegrationTích hợp thay đổi thường xuyênVersion control và kiểm tra tích hợp
Continuous DeliveryLuôn ở trạng thái có thể phát hànhCó thể cần approval trước Production
Continuous DeploymentTự động phát hành sau khi đạt điều kiệnKhông cần manual approval cho từng deployment

CD có thể viết tắt cả Delivery và Deployment; đọc hành vi mô tả trong scenario.

2.4. Use CI/CD in Fabric

Thành phầnVai trò
Git integrationSource control, branches, commits, đồng bộ workspace với repository
Deployment pipelinesPromote Fabric items qua các stage
Fabric REST APIsĐiều khiển và tự động hóa hoạt động CI/CD

Ví dụ hệ thống phân tích doanh thu: GitHub quản lý định nghĩa Notebook/item → Deployment pipeline phát hành Development sang Test/Production → GitHub Actions hoặc Azure DevOps dùng REST APIs để tự động hóa nếu cần.

Exam notes

  • Track changes/history, branches, merge/revert → Git.
  • Promote Fabric content from Test to Production → Deployment pipelines.
  • Automate deploy on a CI event → DevOps workflow + Fabric REST APIs.
  • Validate every Pull Request → cần CI tests, không chỉ Git integration.

Unit 3 — Implement version control and Git integration

Unit này dạy gì

Kết nối Fabric workspace với Git, commit/update theo hai chiều và tổ chức phát triển bằng branches và Pull Requests.

3.1. Connect to a Git Repository

Version control lưu định nghĩa item được hỗ trợ vào repository để theo dõi từng lần thay đổi.

Thuật ngữÝ nghĩa
RepositoryKho mã nguồn và lịch sử thay đổi
BranchNhánh phát triển
CommitBản ghi tập thay đổi
PushĐưa commits lên remote
Pull RequestĐề xuất hợp nhất thay đổi
MergeHợp nhất branches
RevertĐảo ngược hiệu quả thay đổi trước bằng một thay đổi mới

Ví dụ sửa TransformSales để hỗ trợ cột Discount: Git ghi nhận phiên bản; nhóm có thể xác định commit gây lỗi. Khôi phục định nghĩa item không đồng nghĩa tự động khôi phục dữ liệu Lakehouse đã bị thay đổi.

Git integration hỗ trợ các providers được Microsoft công bố như Azure DevOps Services, GitHub và GitHub Enterprise cloud được hỗ trợ. Kết nối đặt ở workspace level, với một repository/branch/folder chọn tại một thời điểm. Không phải mọi item và dữ liệu OneLake đều có cùng mức độ hỗ trợ Git.

Chuẩn bị: Fabric workspace trên capacity hợp lệ; repository; Workspace Admin; tenant cho phép Git; quyền repository và phương thức authentication phù hợp (ví dụ GitHub PAT với phạm vi được yêu cầu).

Các bước:

  1. Fabric → Workspaces → [workspace].
  2. Workspace settings → Git integration.
  3. Chọn GitHub hoặc Azure DevOps.
  4. Xác thực, chọn repository, branch, folder.
  5. Connect; xử lý đồng bộ ban đầu theo trạng thái workspace/repository.

Ví dụ: workspace SalesAnalytics-Dev, repository fabric-sales-analytics, branch main, folder fabric.

Không nhầm: Kết nối Git chỉ tạo quan hệ source control, không tự triển khai Production.

3.2. Commit and update the Fabric workspace and Git repository

flowchart LR
 W[Fabric Workspace] -->|Commit to Git| G[Git branch]
 G -->|Update from Git| W

Workspace → Git: Mở Fabric item và chỉnh sửa; Source control → Changes → Commit ghi định nghĩa được hỗ trợ lên Git branch.

Git → Workspace: Một developer khác sửa định nghĩa rồi push lên repository; trong Fabric sử dụng Source control → Updates → Update để nhận thay đổi về workspace.

Git status có thể phản ánh: workspace thay đổi chưa commit, Git có commits mới, hai bên đồng bộ, hoặc có khác biệt/xung đột cả hai phía. Khi cả hai phía đều sửa, không được cập nhật mù quáng vì có thể ghi đè.

3.3. Branching scenarios

A. Isolated Fabric workspace: Mỗi developer phát triển trên feature branch, gắn với workspace độc lập. Ví dụ:

DeveloperWorkspaceGit branch
ASales-Feature-Afeature/sales-cleaning
BSales-Feature-Bfeature/sales-model
Shared teamSales-Developmentmain

B. Client tools: Dùng Power BI Desktop, VS Code hoặc Git tooling để chỉnh item dưới dạng tệp; đẩy thay đổi lên repository, rồi cập nhật Fabric workspace phù hợp.

3.4. Create a dedicated branch, issue pull requests and sync a workspace with Git

flowchart TD
 A[Main branch + Shared Dev workspace] --> B[Feature branch + Isolated workspace]
 B --> C[Developer changes + Commit]
 C --> D[Pull Request + Review / Tests]
 D --> E[Merge into shared branch]
 E --> F[Update Dev workspace from Git]

Các bước thực tế:

  1. Source control → Branch out to new workspace để tạo feature branch và isolated workspace (nếu chức năng được hỗ trợ/cấp quyền).
  2. Sửa Notebook/Pipeline/item trong workspace mới.
  3. Commit thay đổi lên feature branch.
  4. Tạo Pull Request trên GitHub hoặc Azure DevOps; chạy review/CI theo chính sách nhóm.
  5. Merge vào nhánh chung; shared Development workspace chọn Update from Git.

Quyền và giới hạn: Workspace Admin thiết lập Git connection; tenant phải bật Git integration; capacity tương thích; My Workspace không hỗ trợ; việc commit/update phụ thuộc vào quyền sửa item và Git. Microsoft cũng công bố thay đổi chính sách read-write item vào 28/02/2027 trong tài liệu, nên cần kiểm tra lại khi triển khai.

Unit 4 — Implement deployment pipelines

Unit này dạy gì

Tạo Deployment pipelines, gán các workspaces vào stages và đưa các định nghĩa Fabric item được hỗ trợ qua Development, Test, Production.

4.1. What are deployment pipelines?

flowchart LR
 D[Development workspace] -->|Deploy| T[Test workspace]
 T -->|Deploy| P[Production workspace]
StageMục đíchVí dụ
DevelopmentPhát triển và sửa đổiSửa Notebook
TestKiểm thử, UAT, validationKiểm tra Notebook và Report
ProductionCung cấp chính thứcDashboard doanh thu

Deployment pipeline vs Data Pipeline: Data Pipeline trong Fabric Data Factory điều phối ETL/ELT, còn Deployment pipeline thuộc lifecycle management, chuyển định nghĩa item giữa stages. Dữ liệu Lakehouse không tự sao chép qua các stages chỉ vì item đã được deploy.

4.2. Create a deployment pipeline

  1. Workspaces → Deployment pipelines → New pipeline (hoặc lệnh từ workspace nếu có).
  2. Đặt SalesAnalytics-Release, mô tả và số stages.
  3. Tạo stages Development, Test, Production.
  4. Gán workspace tương ứng: SalesAnalytics-Dev, SalesAnalytics-Test, SalesAnalytics-Prod.

Fabric hỗ trợ 2–10 stages trong một Deployment pipeline theo tài liệu được đối chiếu; số stage xác định lúc tạo và không thể thay đổi tùy ý về sau. Cần role phù hợp để gán workspace. Không nên cấp Contributor hoặc Admin Production cho mọi developer.

4.3. Deploy content to a pipeline stage

Ví dụ Development có TransformSales, Test chưa có:

  1. Mở Deployment pipeline.
  2. Chọn Test stage và xem item differences.
  3. Chọn TransformSales.
  4. Chọn Deploy, xác nhận.
  5. Kiểm tra item tại Test workspace.

Full deployment đưa toàn bộ nội dung phù hợp theo phạm vi triển khai; Selective deployment chỉ đưa các items đã chọn. Nếu chỉ hai trong năm items hoàn tất kiểm thử, có thể dùng selective deployment. Nhưng cần kiểm tra dependencies: Report có thể phụ thuộc Semantic Model chưa tồn tại ở đích.

Item pairing: Fabric thiết lập quan hệ item nguồn–đích để nhận biết item cần update ở lần deploy tiếp theo. Với paired item, Fabric duy trì ID và URL item đích theo cơ chế hỗ trợ thay vì đơn giản xóa/tạo mới mỗi lần.

Autobinding: Khi triển khai SalesReport và SalesSemanticModel cùng nhau từ Dev sang Test, Fabric cố gắng gắn Report-Test với Model-Test thay vì Model-Dev. Tính năng phụ thuộc vào loại item và sự tồn tại của dependency; không tự sửa mọi source connection.

Deployment rules: Cấu hình khác nhau theo stage đối với các item/rule hỗ trợ như data source rules, parameter rules và default lakehouse rules cho Notebook.

Cấu hìnhDevelopmentProduction
Data sourceSQL-DEVSQL-PROD
DatabaseSalesDevSalesProd
DataSampleProduction data

Không mặc định triển khai các nội dung sau: toàn bộ dữ liệu thực tế; Workspace permissions; Item permissions; Workspace settings; data source credentials; Semantic Model refresh schedule; role assignments trên Semantic Model. Triển khai thành công không bảo đảm quyền, dữ liệu và kết nối Production đã đúng.

4.4. Use deployment pipelines with Git

Workflow phổ biến được giảng:

flowchart TD
 G[Git repository] --> D[Development workspace - Git integration]
 D --> T[Test workspace - Deployment pipeline]
 T --> P[Production workspace - Deployment pipeline]
  1. Developer phát triển ở branch riêng.
  2. Merge changes vào shared Git branch.
  3. Development workspace Update from Git.
  4. Deploy Development → Test.
  5. Chạy validation.
  6. Deploy Test → Production.
  7. Kiểm tra data, permissions, credentials, dependencies và refresh.

Đây là một pattern phổ biến, không phải quy tắc cấm Test/Production kết nối Git trong những workflow khác.

Exam notes

  • Deploy không tự copy toàn bộ dữ liệu OneLake.
  • Git integration không tự thay thế Deployment pipelines.
  • Deployment pipeline không phải Data Pipeline.
  • Autobinding có điều kiện và phụ thuộc item types.
  • Deployment rules không áp dụng giống nhau cho mọi item.
  • Deployment success không bảo đảm permissions/credentials/schedules đầy đủ.

Unit 5 — Automate CI/CD using Fabric APIs

Unit này dạy gì

Sử dụng Fabric REST APIs để tự động hóa đồng bộ Git và Deployment pipelines bằng GitHub Actions hoặc Azure DevOps thay vì thao tác portal thủ công.

5.1. Use the Fabric REST APIs for CI/CD to automate processes

Nhóm Git APIs: Get Status; Commit To Git; Update From Git; Connect; Disconnect; Get Connection. Một workflow sau Pull Request merge có thể đọc Git status rồi cập nhật Dev workspace bằng Update From Git.

Nhóm Deployment pipelines APIs: Tạo pipeline; quản lý stage và assignments; lấy danh sách items; gọi deployment; đọc trạng thái tác vụ theo APIs được hỗ trợ.

Ví dụ endpoint tạo pipeline:

POST https://api.fabric.microsoft.com/v1/deploymentPipelines

Request cần access token, permissions/scopes phù hợp (ví dụ delegated Pipeline.ReadWrite.All cho operation được hỗ trợ), tên pipeline và stages.

flowchart TD
 A[Merge Pull Request] --> B[CI validation]
 B --> C{Tests passed?}
 C -->|No| X[Stop release]
 C -->|Yes| D[Update Dev from Git]
 D --> E[Deploy to Test via Fabric REST API]
 E --> F[Test validation]
 F --> G{Approved?}
 G -->|No| X
 G -->|Yes| H[Deploy to Production]
 H --> I[Post-deployment checks]

Security/governance: Microsoft Entra authentication; quyền trên pipeline và workspace; tenant settings; quản lý secrets không commit plaintext vào Git; xử lý lỗi HTTP 401, 403, 429; long-running operations; logging và audit trail. DevOps tools không vượt qua Fabric authorization.

Exam notes

  • Programmatically deploy items → Fabric REST APIs.
  • Automate Git updates → Git REST APIs.
  • Deploy Test/Production → Deployment pipeline APIs.
  • Run on PR merge → DevOps workflow + APIs.

Câu 1 — Git có vai trò gì trong CI/CD Fabric?

  • A. Triển khai thay đổi giữa các môi trường.
  • B. Tự động kiểm thử mọi thay đổi.
  • C. Hỗ trợ version control, branches, cộng tác và lịch sử thay đổi.

Đáp án C. Git quản lý phiên bản và cộng tác. A nhầm với Deployment pipelines. B nhầm với CI tests phải được cấu hình riêng. Mẹo: historical changes/branches → Git. Liên hệ Unit 2, Unit 3.

Câu 2 — Mục đích kết nối workspace với Git?
